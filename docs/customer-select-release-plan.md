# 셀프 고객 서비스 — 출시 작업 계획과 1차 화면 검토안

작성: 2026-09-22. 상태: **정책 합의 완료 / 화면 구성 제안 / 구현 전**.
제품 정책의 기준은 [customer-select.md](customer-select.md) §2.1이다.
이 문서의 화면·권한·전달본은 현재 동작을 설명하는 것이 아니라 구현할 계획이다.

## 1. 작업 및 검토 방식

- 사용자 목적을 끝내는 묶음 단위로 설계 → 구현 → 검증 → 사용자 검토 → 수정·커밋한다.
- 큰 화면 변경은 아래처럼 구조·행동을 먼저 검토한다. 작동하지 않는 별도 목업 앱은 만들지 않는다.
- 구현된 묶음은 실제 접속 경로와 PC·모바일 캡처, 확인한 항목과 남은 문제를 제공한다.
- 흐름·권한·범위에 영향을 주는 미결정 사항은 먼저 질문한다. 일반적인 구현 선택은 자체 판단한다.
- 추가 아이디어는 작업 목록에 배치한다. 합의 없이 첫 출시 범위에서 빼지 않는다.
- 푸시·PR·머지는 별도 승인 후 진행한다. 커밋은 작업 단위로 진행한다.

## 2. 출시까지의 작업 묶음

| 묶음 | 주요 결과 | 완료 검증 |
|---|---|---|
| A. 시작·업로드·현황 | 가벼운 생성, 한도 안내, 프로젝트 현황 접근, 기존 업로드 복구 개선 | 신규/기존/빈 프로젝트, 한도 직전·도달·삭제 후 복구, 업로드 실패·재시도, PC·모바일 |
| B. 혼자·함께 고르기 | 개인 찜·의견과 소유자 최종 선택 분리, 참여자 식별, 공유 중지·재발급, 저장 상태 | 소유자·참여자 API 권한, 동시 입장, 실패·연속 조작, 링크 중지 후 접근 |
| C. 확정·전달·완료 | 확정 결과 보존, TXT·CSV, 읽기 전용 작가 링크, 전달 표시, 다시 열기·새 버전 | 목표 미달·초과, 미저장 변경, 동일 파일명, 재확정 후 이전 결과 불변, 수신자 화면 |
| D. 실시간 협업 | 변경 동기화, 온라인 표시, 같은 사진으로 초대, 따라가기, 임시 대화 | 두 세션/서로 다른 화면 크기, 재접속·중복 이벤트, 수신 동의, 따라가기 종료 |
| E. 후보 정리 | 공통 찜·의견 차이·고민 중·두 장 비교·마지막 위치 복원 | 참여자별 결과 정확성, 필터/삭제 후 위치 복원, 모바일 비교, 대량 사진 |
| 출시 통합 검증 | A~E 연결, 운영 정책과 실제 배포 절차 확인 | 2,000장 실측, 두 사용자 전체 흐름, 저장 실패·재접속, 결과 전달 |
| 후속 선택 기능 | 보정본 업로드·매칭·비교·재보정 | 기본 완료와 독립 진입, 보정본 왕복 검증 후 공개 |

A~E는 모두 첫 출시 범위다. 병렬로 화면을 복제하지 않고 앞 묶음의 공통 UI·권한을 다음 묶음에서 사용한다.
E의 일부는 B에서 같은 코드를 다룰 때 함께 구현할 수 있으나 별도의 검증 항목으로 유지한다.

## 3. 목표 흐름과 역할

소유자: 로그인 → 프로젝트 생성 → 사진 업로드 → 혼자/함께 고르기 → 최종 검토·확정 → 결과 전달 → 완료.
참여자: 초대 링크 → 이름 설정 → 개인 찜·의견 → 내 의견 제출 → 필요하면 다시 의견 수정.
작가: 결과 링크 → 확정 사진·요청사항 확인 → 파일명 목록 다운로드. 로그인 없이 읽기만 가능.

| 행동 | 소유자 | 참여자 | 작가용 결과 링크 |
|---|---|---|---|
| 개인 찜·의견 | 가능 | 가능 | 불가 |
| 최종 선택·확정·전달·다시 열기 | 가능 | 불가 | 불가 |
| 사진 업로드·삭제, 프로젝트 설정·삭제 | 가능(설계 제안) | 불가(설계 제안) | 불가 |
| 공유 링크 관리 | 가능 | 불가 | 불가 |
| 확정 결과 열람 | 가능 | 제공 범위 추후 확인 | 해당 전달본만 |

개인의 의견 제출은 전체 확정이 아니다. 찜하지 않았다는 이유만으로 반대 의견으로 해석하지 않는다.
작가 결과 링크는 협업 링크와 분리하고 특정 전달본에 연결한다. 수정본을 만들 때 기존 링크의 내용을
조용히 교체하지 않는다. 전달 완료는 복사/다운로드와 별개로 사용자가 실제 전달 여부를 표시한다.

## 4. A 묶음: 현재 확인한 것과 변경 범위

현재 코드는 생성 폼에 기본 정보와 일정/작가 정보를 모두 펼쳐 표시한다. 업로드에는 남은 장수,
배치 처리·예상 시간·실패 재시도와 공통 갤러리가 있다. 목록은 사진 수·완료 플래그로 다음 화면을
계산하며 설정 화면에서 수정·삭제를 지원한다. 프로젝트 현황 중심 화면은 없다.

관련 코드:
- `src/app/customer-select/_lib/NewCustomerProjectForm.tsx`
- `src/app/customer-select/page.tsx`, `_lib/project-routing.ts`
- `src/app/customer-select/[projectId]/upload/page.tsx`
- BE `app/routers/customer_upload.py`의 `MAX_PHOTOS_PER_CUSTOMER_PROJECT`

### A1. 내 프로젝트

- ACUT Light 셸과 기존 프로젝트 카드·대표 이미지 규칙을 유지한다.
- 카드에 사진 수, 선택 수/참고 목표, 현재 상태와 한 가지 주요 행동을 표시한다.
- `이어서 고르기`는 작업 화면으로 직행한다. 별도 `프로젝트 현황`과 더보기의 설정으로 접근한다.
- 최초 빈 화면에는 서비스 설명 한 문장과 `사진 선택 시작하기`를 둔다.
- B~D 구현 전에는 온라인 수·의견 제출 수 등 아직 신뢰할 수 없는 정보를 꾸며 표시하지 않는다.

### A2. 프로젝트 생성 — PC/모바일 공통 정보 순서

```text
ACUT                                             내 프로젝트

어떤 사진을 골라볼까요?
프로젝트 이름   [ 예: 우리 웨딩 사진                 ]
고를 사진 수    [ 30 ] 장
               참고 목표예요. 더 고르거나 덜 골라도 괜찮아요.

▸ 촬영일·마감일 등 추가 정보 (선택)

프로젝트당 최대 2,000장까지 올릴 수 있어요.
원본 파일은 직접 보관해 주세요. 선택용 이미지를 저장해요.
─────────────────────────────────────────────────────
                                          [사진 올리기]
```

기존 촬영 유형·촬영일·마감일·스튜디오 입력은 접힌 추가 정보 안에 유지한다.
모바일은 한 열과 하단 주요 버튼, PC는 읽기 쉬운 폼 폭을 유지한다.
목표 미정 옵션은 아직 정책으로 합의하지 않았으므로 이 묶음에서는 기존 숫자 목표를 유지한다.
폴더명으로 자동 생성하는 빠른 시작은 향후 제안으로만 남긴다.

### A3. 업로드 — 사진이 있는 상태

```text
← 내 프로젝트    우리 웨딩 사진          현황  [사진 추가]
1,284 / 2,000장 · 716장 더 올릴 수 있어요
사진 검색                              정렬  사진 정리 도움
─────────────────────────────────────────────────────
                 기존 공통 가상화 사진 갤러리
                   파일 드롭으로 사진 추가
─────────────────────────────────────────────────────
업로드 480 / 800장 · 약 3분 남음                [업로드 중단]
```

- 업로드가 없으면 하단 주 행동은 `사진 고르기`. 사진 삭제 선택 중에는 기존 삭제 행동을 사용한다.
- 모바일은 검색·보조 기능을 좁은 헤더에 모두 밀어 넣지 않고 기존 공통 반응형 패턴을 사용한다.
- 빈 상태: 파일 선택, 지원 형식, 최대 장수, 원본 별도 보관 안내.
- 한도 초과: 선택 장수/가능 장수/초과 장수를 보여준다. 자동 제외 정책은 구현 전 확인한다.
- 실패: 성공 파일은 유지하고 실패 파일명·재시도를 제공한다. 새로고침 후 자동 재개된다고 안내하지 않는다.
- 완료: 한 가지 주요 행동 `사진 고르기`, 보조 행동 `함께 고를 사람 초대`(B에서 연결).
- AI 제안 모달은 기존 동작을 유지하되 `비슷한 사진 묶기` 등 결과 중심으로 설명한다.
- 최대값은 서버 권한/한도 응답을 기준으로 화면에 표시하는 방향을 검토한다. BE에서도 검증한다.

### A4. 프로젝트 현황 — 제안 경로 `/customer-select/[projectId]`

```text
← 내 프로젝트    우리 웨딩 사진                    설정

사진 고르는 중
1,284장 중 24장 선택 · 목표 30장(참고)
                                       [이어서 고르기]

사진 관리     함께 고르는 사람     전달 결과
촬영일 / 선택 마감일 / 작가·스튜디오
```

현황은 별도 필수 경유지가 아니다. 목록의 주요 행동은 바로 작업으로 이동한다.
모바일은 같은 내용을 세로로 배치하고 `이어서 고르기`를 하단에 둔다.
참여자·전달본 영역은 B/C에서 실제 정보와 행동이 갖춰질 때 활성화한다.
단계 표시는 보정본 검토를 필수 단계로 포함하지 않는다.

### A5. 완료 기준

- 신규 사용자가 생성 → 업로드 → 사진 선택으로 이동하고, 목록/현황에서 다시 이어갈 수 있다.
- 생성 시 업로드 한도와 선택 목표의 차이를 이해할 수 있다.
- 성공한 사진만 한도에 집계하고 삭제 후 여유 장수가 갱신된다. 실패 파일은 용량을 차지하지 않는다.
- 한도 초과·실패·중단·재시도·빈 검색 결과가 다음 행동과 함께 표시된다.
- PC와 모바일에서 헤더·하단 버튼·키보드에 주요 내용이 가리지 않는다.
- 기존 대량 갤러리·드래그 업로드·삭제·단축키·예상 시간 기능을 유지한다.
- 실제 2,000장 검증은 완료 여부와 측정 환경을 기록하며 소규모 확인으로 대체하지 않는다.

## 5. 구현 전에 순서대로 확인할 사항

첫 화면 검토에서 확인:
- 간단한 생성 폼과 선택 정보 접기, 필수 경유하지 않는 프로젝트 현황 구성이 적절한가?
- 한도보다 많은 파일 선택 시 업로드 전 재선택을 요청할지, 가능한 파일 목록 확인 후 일부만 올릴지?

B~E 착수 시 확인(아직 확정된 정책 아님):
- 참여자의 별점·의견 공개 범위, 소유자 전용 사진 관리, 선택 기록 있는 사진 삭제 방식.
- 임시 대화의 보관 기간·늦게 들어온 사람의 기록 열람, 참여 인원 상한·다른 기기에서 본인 복구.
- 의견 차이의 정의(예: 참여자 중 일부만 찜), 고민 중의 개인/공용 범위.
- 전달본 이미지 보존과 사진/프로젝트 삭제 시 기존 결과 링크 처리, 결과 링크 중지·만료 정책.

정책이 필요한 묶음에 도달하기 전에 질문하고 기록한다. 구현 편의로 임의 확정하지 않는다.
