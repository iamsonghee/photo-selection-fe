## 1. 배경 — 본식 보정본에서 지금 무엇이 일어나는가

웨딩 본식 보정본(포토샵 내보내기)은 EXIF가 없어 촬영 시각이 없다. 로컬 샘플 두 건(해군결혼식 3,439장, 장준용 1,285장) 모두 EXIF 0개, 1200px JPEG다. 이 경우 clip-service `_run_scene`은 **내용 기준 경로**로 간다.

현재 내용 기준 경로(`clip-service/app/customer_ai.py` `_run_scene`, `scenes.py`):

1. 유사컷용 Gemini 임베딩(`gemini-embedding-2`, 768차원, 300px 썸네일)을 재사용한다.
2. `content_order`가 파일 연번으로 순서를 복원하려 하지만, 정규식(`([^\d]*)(\d{4,})([^\d]*)` fullmatch)이 `0001_OS100353.jpg`처럼 숫자 뒤에 또 숫자가 오는 이름에는 맞지 않아 업로드 순서를 그대로 쓴다. 업로드 순서는 파일 선택창이 준 순서(`upload/page.tsx` `handleFiles`의 `selectedFiles` 순서 → BE `order_index = current_count + order_offset`, `customer_upload.py`)이며 파일명순 정렬은 하지 않는다.
3. `split_by_content`가 앞뒤 `CONTENT_WINDOW=5`장 평균 유사도가 `CONTENT_CUT_SIMILARITY=0.92` 아래로 떨어지는 곳을 자른다. 최소 `CONTENT_MIN_SCENE_PHOTOS=10`장, 최대 `CONTENT_MAX_SCENES=60`구간. 3,439장이면 구간당 평균 57장 이상이다.
4. 구간마다 Gemini Flash-Lite(`GEMINI_FLASH_MODEL`)로 대표 `DESCRIBE_SAMPLE_PHOTOS=5`장을 보고 `place`·`outfits`를 묘사한다(`_describe_scene`, `DESCRIBE_PROMPT_VERSION=describe-v7-specific-background`). 이 프롬프트는 스튜디오 세트·소품·의상 기준이다.
5. 구간별 대표 `SECTION_SAMPLE_PHOTOS=2`장을 한 호출에 모두 넣어 큰 흐름을 정한다(`_plan_content_sections`, `basis = outfit | activity`, 이름은 자유 서술).
6. `size_content_sections`가 유사컷을 접은 카드 수가 `CONTENT_VISIBLE_MAX=120`을 넘는 구간만 내용 경계에서 같은 이름으로 나누고, `number_repeated`가 번호를 붙인다.
7. 웨딩 본식 카탈로그(`src/lib/customer-shoot-scenes.ts` `wedding_ceremony.scenes` 8개)는 이 경로에서 **쓰이지 않는다**(`to_name`은 `by_content`면 묘사 호출로 간다).

해군결혼식 샘플의 실제 결과: LLM은 "하객 맞이 및 피로연", "본식 식순 및 예식 진행", "기념 촬영 및 디테일 컷" 세 덩어리만 만들었고, 화면의 11개 장면("예식 진행 1~4", "디테일 컷 1~6")은 120카드 기준 크기 분할 조각이다. 번호만 다른 장면이라 고객에게 의미가 없다.

이미 있는 평가 장치: `/admin/scenes`(`customer_scene_labels`, `src/lib/scene-label-score.ts`)가 정답 경계·이름을 저장하고 경계 정밀도·재현율(`TOLERANCE=3`장)과 이름 정확도(번호 제거 후 비교)를 낸다. 운영자가 같은 화면에서 AI 정리를 다시 돌릴 수 있다.

## 2. 목표와 지표

목표: 촬영 유형이 **웨딩 본식**인 프로젝트에서 `AI로 장면 정리`가 "신부대기실, 신랑 입장, 예식, 축가·축하공연 …"처럼 **고정 단계 목록의 이름**으로, **시간 순서대로 이어진 장면**을 만든다. 사진이 없는 단계는 장면이 생기지 않는다.

지표(`/admin/scenes` 점수 그대로):

| 지표 | 현재(해군 샘플) | 목표(1차) |
|---|---|---|
| 이름 정확도(사진 단위, 정답 이름 = AI 이름) | 측정값 없음. 단계 이름이 없어 사실상 0 | 큰 단계(대기실·하객 맞이·예식·기념촬영·피로연) 80% 이상 |
| 경계 재현율(정답 경계 ±3장 안에 AI 경계) | 측정값 없음 | 80% 이상 |
| 경계 정밀도 | 측정값 없음 | 80% 이상(과분할 억제) |
| 추가 Gemini 비용 | — | 흔들림 판정 입력 토큰 +약 9% 이내, 추가 호출 0 |

목표 수치는 홈스냅 실험(실촬영 459장·1,572장, 경계 8/8·11/12)과 단계 간 시각적 구분 가능성에서 잡은 **기대치**다. 1차 측정 뒤 조정한다. 2026-10-15 실측과 비용 변화(단계 판정을 따로 묻는 호출 추가)는 §5.2.

## 4. 설계안 (planned)

### 4.1 적용 구조 — 사진 단위 판정 + 순서 다듬기 (홈스냅 `sceneByPlace` 재사용)

홈스냅이 이미 쓰는 구조를 본식에 적용한다. 새 파이프라인을 만들지 않는다.

1. FE 카탈로그의 `wedding_ceremony`에 단계 목록과 `sceneByStage: true`(구현에서 홈스냅의 `sceneByPlace`와 구분되는 플래그로 확정, §5.1)를 둔다. 그러면 `AiTidySheet.tsx` `startAiTidy`와 관리자 `ai/route.ts`가 흔들림 판정·장면 요청에 `placeNames`·`placeBasis`·`placeHints`를 같이 보낸다(`/api/customer-select/projects/[id]/ai/[kind]` → `place_names`·`place_basis`·`place_hints`).
2. clip-service `_run_quality`가 사진 한 장당 한 번 보내는 Gemini 호출의 응답 스키마에 `place` 필드를 더한다(`gemini_quality_client.py` `customer_schema`). 이 필드는 `Literal[목록 + "알 수 없음"]` enum이라 모델이 목록 밖 이름을 만들 수 없다. 프롬프트 버전은 `v1-people-place-<목록 해시>`(`quality_prompt_version`)라 목록이 바뀌면 다음 정리 때 전체를 다시 판정한다.
3. 판정이 끝나면 `_place_scenes` → `split_by_place`가 라벨을 앞뒤 `PLACE_WINDOW=29`장 다수결로 다듬고, 라벨이 바뀌는 곳에서 자르고, `PLACE_MIN_RUN=12`장 미만 구간은 긴 이웃에 붙인다. 이름은 라벨 그대로, 반복은 `number_repeated` 번호. `_run_quality` 끝에서 `_replace_scenes`로 장면을 교체하고 `_mark_place_scenes`로 실행 설정에 남긴다.
4. 사진이 없는 단계는 구간이 안 생기므로 장면 목록에 나오지 않는다. "알 수 없음"은 다듬기에서 앞 라벨로 채워진다.

왜 사진 단위인가: 지금 문제의 절반은 이름이 아니라 **덩어리 크기**다. 구간 묘사 호출에 목록만 끼우면 60구간 상한과 120카드 분할이 그대로 남는다. 사진 단위 라벨은 단계 길이에 맞춰 경계가 생기고, 추가 호출 없이 기존 흔들림 호출에 얹힌다.

한계(§8에서 대응): 사진 한 장만 보므로 성혼선언과 덕담처럼 같은 자리에서 말하는 단계는 갈리지 않는다. 다듬기 창·최소 구간 값은 홈스냅 실측값이라 본식에 다시 맞춰야 한다.

### 4.3 업로드 순서 보장

다듬기(다수결)는 사진 순서가 맞다는 전제에서만 동작한다. 촬영 시각이 없으면 `order_index`가 유일한 순서다.

결정(2026-10-14, 둘 다 적용):
- FE `upload/page.tsx` `handleFiles`: 선택한 파일 묶음을 큐에 넣기 전에 파일명 기준 자연 정렬(`localeCompare(…, { numeric: true })`, 이미 정렬 화면이 쓰는 방식)로 안정 정렬한다. 촬영 시각이 있는 사진은 `capture_order`가 시각으로 다시 정렬하므로 영향이 없다.
- clip-service `content_order`: 앞자리 연번(`^(\d{4,})_`)도 단일 연번으로 인정한다. 샘플 두 건의 이름(`0001_OS100353.jpg`, `0001_SJ7_3213.jpg`)이 여기에 해당한다. 기존 조건(한 체계·중복 없음·범위 10배 이내)은 유지한다.

이미 업로드된 샘플 프로젝트는 재업로드 없이 `content_order` 확장만으로 순서가 복원되는지 먼저 확인한다. 장준용 프로젝트는 §6 단계 0에서 역순·일부 섞임을 확인했고, 파일명이 전부 연번이라 확장만으로 복원된다. 유사컷 묶기(`capture_order`)는 `order_index`를 그대로 쓰므로 섞인 구간에서 연속 촬영을 놓칠 수 있다 — 이번 범위 밖, §10에 기록.

### 4.4 첫 결과(중간 상태) 처리 — A로 결정(2026-10-14)

홈스냅 구조에서는 장면 실행이 먼저 시간 기준 장면을 보여주고, 흔들림 확인이 끝나면 장소 기준으로 교체된다. 본식 보정본은 시각이 없으므로 장면 실행이 **지금의 내용 기준 경로(묘사 호출 최대 60회 + 큰 흐름 호출 1회)** 를 먼저 돌린 뒤 흔들림 완료 시점에 단계 장면으로 교체된다. 이 첫 결과는 버려지는 비용이고 고객에게 "예식 진행 1~4" 같은 화면을 잠깐 보여준다.

선택지:
- A. `place_names`가 있는 촬영 유형에서 시각 없는 사진은 장면 실행이 내용 기준 경로를 건너뛰고(묘사·큰 흐름 호출 없음), 흔들림 확인 완료를 기다려 단계 장면만 저장한다. 그동안 화면은 "촬영 시간순 전체 보기 + 진행 상태"(지금의 정리 중 화면). 비용·혼란 최소. 단, 흔들림 확인이 실패하면 장면이 없다.
- B. 지금처럼 내용 기준 장면을 먼저 보여주고 교체한다. 코드 변경 최소, 비용 중복.

결정: A. 구현 방식: 본식(시각 없음 + `place_names`)의 장면 실행은 내용 기준 경로를 돌리지 않고 **흔들림 실행이 끝날 때까지 `processing` 상태로 기다린다**(60초 heartbeat 유지, `_ensure_running`으로 대체 여부 확인). 흔들림이 완료되면 `_place_scenes`로 단계 장면을 저장하고 완료, 흔들림이 실패하면 장면 실행도 실패로 닫는다. 그래서 FE 상태 기계(`none/analyzing/ready/fallback`)는 바뀌지 않고 배너가 끝까지 유지된다. 실패 시 대체는 "장면 없음 + `AI 정리 다시 시도`"(이미 있는 실패 UI). FE `useSceneAnalysis.ts`의 `byPlace` 진행 문구("장소를 보고 장면 다듬는 중")는 본식용 문구로 분기한다(문구는 PRD §3).

### 5.1 구현에서 확정한 값과 계획과 달라진 점 (2026-10-14)

- **단계별 판단 기준을 판정 문구에 넣는다.** 이름만으로는 신부 입장과 행진처럼 구도가 비슷한 단계가 섞이기 쉬워, FE 카탈로그에 단계마다 짧은 기준(`sceneHints`, `WEDDING_CEREMONY_STAGES` in `src/lib/customer-shoot-scenes.ts`)을 두고 `place_hints`로 보낸다. 목록을 고칠 때 FE만 바꾸면 된다(clip-service 재배포 불필요). 기준을 바꿔도 판정 버전 해시가 바뀌어 전체 재판정된다.
- **장소 문구는 그대로 두고 단계 문구를 따로 둔다.** `place_basis`(`place`|`stage`)로 고른다. 홈스냅 판정 버전(`…-place-<목록 해시>`)은 바뀌지 않아 기존 판정 캐시가 그대로 쓰인다. 단계 버전은 `…-stage-<목록·기준·STAGE_PROMPT_VERSION 해시>`.
- **다듬기 값(실측 전 시작값):** 창 21장(`STAGE_WINDOW`), 최소 구간 10장(`STAGE_MIN_RUN`), 판정 비율 50%(`STAGE_MIN_LABELED_RATIO`) — 모두 `clip-service/app/scenes.py`. 홈스냅 값(29·12·80%)은 그대로.
- **연번 복원:** 앞자리 연번은 4~6자리만 인정한다(`CONTENT_FILENAME_LEADING_MAX_DIGITS=6`) — `20261008_102030.jpg`의 8자리 날짜를 연번으로 오인하지 않게. 장준용 프로젝트 실제 파일명 1,285장으로 1~1285 순서 복원을 확인했다(읽기 전용 조회).
- **결정 A 구현:** 본식 장면 실행은 같은 정리의 흔들림 실행이 끝날 때까지 기다린다(`_wait_for_quality`: 10초마다 확인, 장면 요청이 먼저 와도 120초 안에 시작된 흔들림 실행을 같은 정리로 보고, 그 뒤에는 최근 흔들림 결과를 쓴다. 멈춘 흔들림 실행은 실패). 이 모드에서 흔들림 실행은 장면을 저장하지 않는다(장면 실행이 저장) — 두 실행이 같은 장면을 두 번 지우고 넣지 않게.
- **장면 실행 요청에도 라벨 옵션을 보낸다:** 장면 실행이 같은 판정 버전을 찾아야 하므로 `scene` 요청에도 `place_names`·`place_basis`·`place_hints`를 보낸다(홈스냅도 같은 목록을 보내며 동작은 같다).

- **사진 순서(FE):** 장면 안·고르기 화면·관리자 검수 화면이 파일 수정 시각으로 정렬해 역순으로 올라간 보정본이 거꾸로 보이고 검수 화면에서 AI 장면이 38번 끊겼다. clip-service와 같은 규칙의 `captureOrder`(`src/lib/customer-scenes.ts`)로 바꿨다.

**실제 엔진 경로 확인:** 짱쭌 1,285장을 흔들림 실행과 같은 순서·배치·맥락으로 `judge_stages`에 넣고(DB 쓰기 없음, 161회 호출, 실패 0, $0.20) 장면 엔진 전체를 거쳤다: 사진별 88.2%, 장면 93.4%, 장면 12개, P3/R3 73/73. 같은 설정 실험(94.7%)과의 차이는 묶음 경계 위치와 실행마다의 응답 차이다. 이어 사용자가 로컬 고르기 화면에서 `AI 다시 정리`로 끝까지 돌렸다(2026-10-15): 흔들림 1,285회 + 단계 161회, 실패 0, 입력 2,655,253·출력 130,678토큰(약 $1.12, 흔들림 재판정 포함), 흔들림 약 10분. 저장된 장면은 위 확인과 장면 크기까지 같았고(사진 93.4%, 12개, 관리자 검수 점수 경계 73%/73%·이름 93%), 화면은 식 전 3·본식 7·식 후 2개. 남은 오판정 중 장면으로 보이는 것은 `신부 입장 (이어서)` 30장(1016~1045) — 신랑 축가 뒤 버진로드에 홀로 선 신부에게 신랑이 다가가 안는 장면으로, 정답도 축가·예식 경계가 애매하다. 이 실행에서 장면 실행이 흔들림 완료 뒤 2분 더 기다린 문제(유사컷 대기를 대기 시작 시각 기준으로 판단)를 찾아 장면 실행 시작 기준으로 고쳤다(`_wait_for_run(since=…)`).

**해군 끝까지 정리(2026-10-15, 로컬 `AI 다시 정리`):** 첫 시도는 Gemini 선불 크레딧 소진(402 `RESOURCE_EXHAUSTED`)으로 1,171장만 판정되고 판정 비율 50% 미만이라 장면 실행이 기존 장면을 지우고 장면 0개로 끝났다(약 $1.03). 충전 뒤 다시 정리는 남은 2,268장만 판정했다(실패 0, 약 $1.98, 흔들림 약 26분, 장면 실행은 흔들림 완료 23초 뒤 끝남 — 대기 수정 반영). 저장된 장면 26개, 사진 정확도 84.9%(카메라 1 92.0%, 카메라 2 76.4%), 관리자 검수 점수 경계 48%/40%·이름 85%(정답 31구간은 파일 순서 기준이라 본식이 두 번 나온다). 화면은 식 전 9·본식 14·식 후 3개 — 본식이 한 번만 나오고 순서는 화촉점화 → 신랑 입장 → 신부 입장 → 예식 → … → 행진이지만, 카메라 2의 오판정 구간이 짝을 못 찾고 상대 위치로 끼워져 `예식 (이어서)`·`축가 (이어서)`·`화촉점화 (이어서)`·`신부 입장 (이어서)`가 여러 번 나온다. 남은 오판정은 카메라 2 식 전 연출 → 신부대기실(138장), 축가 → 예식(82), 화촉점화 → 예식(74).
**이번 실패로 드러난 약점과 수정(2026-10-17):** ① 판정이 대량 실패해 단계가 부족하면 장면 실행이 기존 장면을 지우고 완료로 끝났다 → 흔들림 실행의 `failed_count`가 있고 단계가 부족하면 실패로 닫고 기존 장면을 남긴다. ② 흔들림 실행이 끝날 때 다른 버전 판정 행을 모두 지워 새 판정이 실패한 사진은 이전 흔들림 표시까지 잃었다 → 지금 판정이 있는 사진의 다른 판정만 지운다(`CLEANUP_PHOTOS=200`장씩). 홈스냅 등 다른 촬영 유형의 흔들림 확인에도 같이 적용된다.
**짝 없는 작은 구간 흡수(측정만, 2026-10-17):** 해군 본식의 `(이어서)` 조각을 줄이려고 카메라를 합칠 때 짝 없는 작은 구간을 이웃에 붙여 봤다(저장 판정·실험 판정 각각). 20장 미만: 84.9 → 83.9%, 본식 14 → 11개. 30·40장 미만: 84.2%, 본식 5개지만 축가 장면이 사라짐(정답 축가 약 127장). 60장 미만: 82.1%. 정확도가 오르지 않고 진짜 축가가 사라져 넣지 않았다(측정 스크립트 `a-cut/analysis/scene-experiments/check_absorb.py`).

**비용 변화:** 단계 판정 호출이 1,000장당 약 $0.16 늘고(사진 8장당 1회), 흔들림 호출의 단계 필드(입력 +약 9%)는 빠진다. 단계 판정 버전이 바뀌면 흔들림까지 다시 판정한다(같은 행·같은 버전) — 1차 판정을 받은 프로젝트(로컬 짱쭌)는 다음 정리에서 흔들림 판정 비용이 다시 든다.

## 10. 후속 과제 (비범위)

- 피사체형 태그: 하객·혼주 반응, 소품·디테일, 신랑신부 반응을 인물 칩(`people`)처럼 사진 단위 필터로. 같은 흔들림 호출에 enum 필드 하나를 더 얹으면 되나 프롬프트 버전이 바뀌어 전체 재판정이 필요하므로 단계 목록 확정과 같은 시점에 묶어서 결정.
- 해군 프로젝트를 로컬 정리로 끝까지 돌려 다중 카메라 합치기를 화면에서 확인(약 $3~4: 흔들림 재판정 + 단계 판정).
- 흔들림 판정과 단계 판정 캐시 분리: 지금은 한 행·한 버전이라 단계 문구만 바뀌어도 흔들림까지 다시 판정한다. 분리하려면 저장 위치(DB 변경)가 필요하다.
- 사람이 확인한 정답으로 재채점, 같은 설정 반복 실행으로 편차 측정.
- `clip-service/scripts/quality_cost_experiment.py`는 Gemini 키를 URL 파라미터로 보낸다 — 오류 메시지에 키가 찍힐 수 있어 헤더(`x-goog-api-key`)로 바꾸는 것이 좋다.
- 유사컷 묶기 순서: 촬영 시각 없는 사진은 `capture_order`가 `order_index`를 쓰므로 업로드 순서가 섞이면 이웃 비교가 어긋난다. 장면과 같은 `content_order` 복원을 유사컷에도 적용할지 별도 판단(기존 유사컷 결과가 바뀌므로).
- 웨딩 촬영(`wedding_shoot`)·돌잔치 등 다른 유형에 같은 구조를 적용할지는 각 유형의 검수 점수를 본 뒤 별도 계획.
