## 1. 문제와 목표

촬영 유형이 **웨딩 본식**인 셀프 고객 프로젝트에서 `AI로 장면 정리`를 돌리면, 보정본에 촬영 시각이 없어 장면이 "본식 식순 및 예식 진행 1~4"처럼 번호만 다른 조각으로 나온다(원인: 계획서 §1). 고객은 "신부대기실", "신랑 입장"처럼 본식 단계로 사진을 찾고 싶어 한다.

목표: 웨딩 본식 프로젝트의 AI 정리 결과가 **고정된 본식 단계 이름**으로, **시간 순서대로 이어진 장면**으로 나온다. 사진이 없는 단계는 보이지 않는다. 다른 촬영 유형의 동작은 바뀌지 않는다.

성공 지표는 계획서 §2(관리자 검수 점수)와 같다. 이 문서는 지표를 다시 정하지 않는다.

## 2. 대상 사용자와 시나리오

| 사용자 | 시나리오 |
|---|---|
| 프로젝트 소유자(셀프 고객) | 보정본 1,000~3,000장을 올리고 `AI로 장면 정리`를 눌러 단계별로 사진을 고른다. 정리 뒤 사진을 더 올리면 `AI 다시 정리`로 갱신한다 |
| 참여자(지인 초대) | 소유자가 정리한 장면을 같은 이름·같은 순서로 보며 찜한다. 정리를 시작하거나 다시 돌릴 수 없다(현재와 같음) |
| 운영자(관리자) | `/admin/scenes`에서 정답 경계·이름을 남기고 점수를 본다. `AI 정리 실행`으로 고객 프로젝트를 직접 정리할 수 있다(비용 발생, 현재와 같음) |

## 3. 화면 상태와 문구

고르기 화면(`/customer-select/[projectId]/select`)의 분석 상태는 현재 `none` / `analyzing` / `ready` / `fallback` 네 가지다. 웨딩 본식은 이 상태 기계를 바꾸지 않고, `analyzing`이 끝나는 시점과 `analyzing` 중 문구만 달라진다.

### 3.1 정리 전 (`none`, 현재와 같음)

- 촬영 시간순 전체 사진. 시각이 없는 보정본은 업로드 순서(파일명 정렬 적용 뒤에는 파일명 순).
- 소유자에게만 `AI로 장면 정리` 버튼. 누르면 `AI로 사진 정리` 시트.
- 시트 문구(현재): "N장을 정리해요. 장면별로 나누고, 비슷한 사진은 묶고, 흔들린 사진은 따로 모아요. 지우는 사진은 없어요." / "사진 수에 따라 몇 분 걸릴 수 있고, 그동안에도 사진을 고를 수 있어요."
- 변경: 웨딩 본식일 때 한 줄 추가 — **"본식은 신부대기실·입장·예식처럼 단계별로 나눠요."** (해요체, 시트 기존 문체)

### 3.2 정리 중 (`analyzing`)

현재: 장면 실행이 진행 중인 동안 상단 배너에 진행 중인 작업을 한 줄씩("장면 나누는 중", "비슷한 사진 묶는 중 · 840 / 2,000장", "흔들림·눈 감음 확인 중 · …장")과 "그동안 마음에 드는 사진에 ♡를 눌러 두세요. 정리가 끝나면 장면별로 모아서 보여드릴게요."를 보인다. 전체 사진은 그대로 고를 수 있다.

변경(계획서 §4.4 결정 A): 웨딩 본식은 **흔들림·눈 감음 확인이 끝날 때까지 장면 실행이 진행 중으로 남는다.** 그래서 배너가 끝까지 유지되고, 중간에 번호 조각 장면이 보이지 않는다.

- 배너의 장면 줄 문구: 현재 "장면 나누는 중"(총 수 0일 때) 대신 **"장면 단계 나누는 중 · 흔들림 확인 뒤 끝나요"**. 홈스냅의 "장소를 보고 장면 다듬는 중" 문구는 그대로 둔다(촬영 유형별 분기).
- 흔들림 줄은 현재 문구·진행 수 그대로("흔들림·눈 감음 확인 중 · n / N장"). 배너의 진행 막대는 현재 장면 진행만 따르므로, 본식은 흔들림 진행 수를 막대에 쓴다.
- 예상 시간: 1,285장 약 10분, 3,439장 약 25분(계획서 §7). 시트의 "몇 분 걸릴 수 있어요"를 유지하고 분 단위 예측은 표시하지 않는다.
- 참여자도 같은 배너를 본다(현재와 같음). 시작 버튼은 없다.

### 3.3 완료 (`ready`)

- 현재와 같이 "장면별로 보기" 제안이 뜨고, 왼쪽 장면 목록(PC 사이드바 / 모바일 퀵메뉴)에 장면 이름이 보인다.
- 변경: 장면 이름은 **본식 단계 목록 안의 값만** 나온다. 사진이 없는 단계는 목록에 없다.
- 장면 목록 표시(2026-10-15 결정·구현): 장면을 **식 전 / 본식 / 식 후** 구획으로 묶는다. 같은 구획에서 다시 나온 단계는 번호 대신 **"예식 (이어서)"**로 적는다(저장된 이름 `예식 2`는 화면에서만 바꿈).
  구획마다 제목·`N개 장면`·구분선, 지금 장면이 있는 구획 제목 강조. 구획 제목이 없는 한 줄 표시는 `식 후 · …`처럼 구획 이름을 앞에 붙인다. 적용 범위는 웨딩 본식만. 상세는 `customer-select.md` "웨딩 본식 장면 묶음".
- "알 수 없음" 라벨은 장면 이름으로 나오지 않는다(다듬기에서 앞 단계로 채움). 모든 사진이 알 수 없음이면 3.4의 대체 상태.
- 완료 직후 안내 한 줄: 홈스냅의 "장소를 보고 장면을 다시 나눴어요" 대신 본식은 안내 없음(처음부터 단계 장면이므로 "다시 나눴다"는 설명이 맞지 않음).

### 3.4 대체·실패 (`fallback`)

- 흔들림 확인이 실패하면 단계 장면을 만들 수 없다. 장면 실행도 실패로 닫고, 현재 실패 UI 그대로 **"AI 정리 실패 · 다시 시도"**(누르면 다시 정리 시트)를 보인다. 사진은 촬영 시간순(= 파일명 순) 전체 보기.
- 흔들림 확인이 일부만 실패(`failed_count > 0`)하면 판정된 사진으로 장면을 만들고, 현재 문구 "흔들림·눈 감음 확인 N장 못 함 · 다시 시도"를 보인다.
- 판정이 대량 실패해(Gemini 크레딧 소진·장애) 단계가 있는 사진이 50%에 못 미치면 장면 실행을 실패로 닫고 **기존 장면을 그대로 둔다**. 화면은 "AI 정리 실패 · 다시 시도", 실패한 사진의 이전 흔들림 표시도 남는다. 다시 정리하면 실패한 사진만 다시 판정한다(2026-10-17, 해군 첫 시도에서 장면이 지워진 문제).
- 사진이 100장 미만(`MIN_PHOTOS_FOR_SCENES`)이면 현재와 같이 장면 없이 전체 보기. 시트의 "장면은 사진이 100장 이상일 때 나눠요" 유지.

### 3.5 다시 정리

- 현재: `보기 옵션` → `AI 다시 정리`("새로 올린 N장까지 장면·유사컷을 다시 나눠요" / "고른 사진·찜·메모는 그대로예요"). 정리 뒤 새로 올린 사진은 다시 정리 전까지 "새로 올린 사진" 장면에 모인다.
- 변경 없음. 단, 단계 목록이 바뀐 뒤 처음 다시 정리할 때는 흔들림 판정이 전체 사진에 다시 돌아 처음 정리와 같은 시간이 걸린다. 시트 문구는 바꾸지 않는다(사용자는 목록 변경을 모른다).
- 이미 정리한 본식 프로젝트는 배포 뒤 자동으로 바뀌지 않는다. `AI 다시 정리`를 눌러야 단계 장면이 된다.

### 3.6 관리자 검수 (`/admin/scenes/[projectId]`)

- 변경 없음. `AI 정리 실행`은 고객과 같은 옵션으로 돌며 비용 확인 창을 띄운다. 정답 이름 입력의 자동완성 목록(`datalist`)은 촬영 유형의 장면 목록을 쓰므로 본식 단계 목록이 자동으로 나온다.

## 4. 기능 요구사항과 수용 기준

각 항목은 테스트 또는 수동 확인으로 판정할 수 있게 적는다. 번호는 계획서 §5 변경 지점과 대응한다.

| # | 요구사항 | 수용 기준 |
|---|---|---|
| R1 | 웨딩 본식 프로젝트의 AI 정리는 본식 단계 목록으로 장면 이름을 붙인다 | 정리 완료 뒤 `customer_scenes.name`이 모두 단계 목록 값(번호 접미사 제외) 중 하나다. `기타 장면`·자유 서술 이름이 없다 |
| R2 | 장면은 시간 순서대로 이어진 구간이다 | 각 장면의 사진이 복원된 순서(파일명 연번)에서 연속 구간이다. 장면 순서 = 구간 순서. 카메라별로 따로 내보낸 파일(R13)은 카메라마다 연속 구간이고, 같은 단계는 카메라마다 한 구간씩 한 장면에 모인다 |
| R3 | 사진이 없는 단계는 보이지 않는다 | 장면 목록에 사진 0장인 장면이 없다(현재 `namedFromAi`가 빈 장면을 거르는 동작 유지) |
| R4 | 번호 조각 장면이 생기지 않는다 | 같은 이름 뒤 번호는 **떨어진 반복**에만 붙는다. 크기 분할(`CONTENT_VISIBLE_MAX`)로 같은 이름이 연속 생성되지 않는다 |
| R5 | 정리 중에는 중간 장면을 보이지 않는다(결정 A) | 흔들림 확인 완료 전까지 장면 실행 상태가 `processing`이고 배너가 유지된다. 그동안 `customer_scenes`가 바뀌지 않는다 |
| R6 | 본식에서는 내용 기준 경로(묘사·큰 흐름 호출)를 돌리지 않는다 | 장면 실행 `usage`에 Flash 호출이 0건. 단위 테스트로 묘사 함수 미호출 확인 |
| R7 | 흔들림 확인 실패 시 실패 UI로 간다 | 흔들림 실행 `failed` → 장면 실행 `failed` → 화면 "AI 정리 실패 · 다시 시도" |
| R8 | 업로드 순서가 파일명 순서를 따른다 | 파일 선택 뒤 큐에 들어가는 순서가 파일명 자연 정렬 순. `order_index`가 그 순서로 저장된다 |
| R9 | 이미 올린 프로젝트도 재업로드 없이 순서를 복원한다 | 앞자리 연번(`^\d{4,}_`) 파일명이면 `content_order`가 번호순으로 복원한다. 장준용 프로젝트(역순 업로드)에서 복원 결과가 1~1285 순 |
| R10 | 다른 촬영 유형의 동작은 바뀌지 않는다 | 홈스냅·돌잔치·웨딩 촬영의 장면 규칙 테스트(골든 케이스 포함)가 그대로 통과한다. 홈스냅 문구("장소를 보고 …")가 유지된다 |
| R11 | 참여자는 소유자와 같은 장면을 본다 | 같은 프로젝트를 참여자 세션으로 열면 장면 이름·순서가 같다. 시작 버튼 없음 |
| R12 | 목록이 바뀌면 다음 정리에서 전체를 다시 판정한다 | 프롬프트 버전 해시가 바뀌고 `customer_quality_assessments`가 새 버전으로 교체된다. 사진마다 한 행만 남기되, 새 판정에 실패한 사진은 이전 판정을 남긴다(2026-10-17) |
| R13 | 카메라별로 따로 내보낸 보정본도 본식이 한 번만 나온다(2026-10-15) | 카메라 A 전체 뒤에 카메라 B 전체가 이어진 파일(해군 `0001_OS1…`~`1865`, `1866_OS2…`~)에서 두 카메라의 같은 단계(예식·행진 등)가 한 장면으로 합쳐지고, 장면 순서가 식 전 → 본식 → 식 후다. 두 카메라가 시간순으로 섞인 파일(짱쭌 SJ7·SJ8)은 그대로 파일명 순서 |
| R14 | 장면 안 사진은 촬영 순서로 보인다(2026-10-15) | 촬영 시각이 없는 보정본은 파일명 연번 순(역순으로 올라가도), 고객 고르기·관리자 검수 화면이 같은 순서. 파일 수정 시각은 순서에 쓰지 않는다(`captureOrder`) |

## 5. 경계 사례

| 상황 | 기대 동작 |
|---|---|
| 이미 정리한 본식 프로젝트(배포 전 결과) | 옛 장면 유지. `AI 다시 정리`를 눌러야 단계 장면. 보기 설정(묶어 보기·흔들림 빼기)은 바뀌지 않음 |
| 정리 뒤 사진 추가 | 새 사진은 "새로 올린 사진" 장면(현재). 다시 정리하면 새 사진만 흔들림 판정하고 장면은 전체를 다시 나눔 |
| 촬영 유형을 다른 값에서 본식으로 바꾼 뒤 정리 | 목록 해시가 달라 전체 재판정. 이전 유형의 장면은 교체됨 |
| 촬영 유형을 본식에서 다른 값으로 바꾼 뒤 정리 | 그 유형의 규칙(시간 기준 등)으로 돌아감. 본식 라벨은 쓰이지 않음(`_place_scenes`가 목록 불일치로 `None`) |
| 100장 미만 | 장면 없음(현재). 흔들림 판정은 돌고 라벨도 남지만 장면을 만들지 않음 |
| 일부 사진에만 EXIF 촬영 시각 | 라벨이 80% 이상이면 단계 기준. 시각이 있는 사진의 10분 이상 공백은 현재 홈스냅 규칙대로 항상 자름. 시각 있는 사진이 80% 미만이면 업로드 순서(= 파일명 순)로만 다듬음 |
| 파일명이 연번이 아닌 보정본(여러 카메라 원본명, `IMG_1234.jpg` 등) | 업로드 순서 그대로. FE 파일명 정렬이 들어가므로 이름순으로 올라감. 이름순이 촬영순이 아닐 수 있다는 안내는 이번 범위 밖 |
| 카메라별로 따로 내보내 이어 붙인 보정본 | 카메라 이름(앞 연번·끝 4자리 번호를 뺀 파일명)이 한 덩어리씩 이어지고 카메라마다 100장 이상이면 카메라마다 단계를 다듬고 합친다(R13). 한 카메라가 100장 미만이거나 덩어리가 쪼개져 있으면 파일명 순서 그대로 다듬는다 |
| 식 전 빈 홀에서 버진로드를 걷는 리허설 컷 | 사진 판정은 행진으로 나올 수 있지만 본식 범위 밖이라 이웃 단계(연출촬영·대기실)로 돌린다. 식 전 묶음에 "행진·퇴장"이 따로 생기지 않는다 |
| 모든 사진이 "알 수 없음" | 라벨 80% 미만 → 단계 장면 없음 → 장면 없이 전체 보기 + 흔들림 결과만 반영. 실패 문구는 아님 |
| 흔들림 확인이 10분 넘게 멈춤(서비스 재시작 등) | 현재 규칙대로 실패로 닫힘(`STALE_RUN_SECONDS`). 장면 실행도 대기 중 heartbeat를 유지하다 함께 실패 → R7 |
| 같은 프로젝트를 두 탭에서 정리 시작 | 현재와 같이 두 번째는 409로 진행 중 상태를 이어 봄 |
| 운영자가 검수 화면에서 실행 | 고객 화면과 같은 결과. 고객에게도 그대로 보임(현재와 같음) |

## 6. 비기능 요구사항

- 비용: 단계 판정을 이어 찍은 10장 묶음으로 따로 묻는다 — 사진 8장당 1회, 1,000장당 약 $0.16(낮은 해상도, 표준 단가). 흔들림 호출에는 단계 필드가 없다. 본식의 내용 기준 경로가 사라져 묘사·큰 흐름 호출이 줄어든다(계획서 §5.2·§7). 비용이 드는 실행은 사용자 확인(시트·관리자 확인 창) 뒤에만 시작한다(현재 유지).
- 시간: 장면이 보이는 시점이 흔들림 확인 완료 시점으로 늦어진다(1,285장 약 10분, 3,439장 약 25분, 표준 티어 `GEMINI_QUALITY_CONCURRENCY=4` 기준). 그동안 고르기는 막히지 않는다.
- 안정성: 장면 실행이 흔들림을 기다리는 동안 60초 heartbeat를 유지한다(`HEARTBEAT_SECONDS`). 서비스 재시작 뒤 멈춘 실행은 10분 뒤 실패로 닫히고 다시 시도할 수 있다.
- 데이터: 기존 고른 사진·찜·메모·참여 색은 장면이 바뀌어도 사진에 붙어 있어 유지된다(현재 구조). DB 스키마 변경 없음.
- 개인정보·로그: 사진 바이트·API 키·판정 원문은 로그에 남기지 않는다(현재 규칙).

## 7. 검증 계획

변경 위험도는 `CLAUDE.md` 기준 **Level 3**(업로드 순서, 사용자 흐름, FE+BE 연동)이다.

단위 테스트(clip-service `tests/test_customer_scenes.py`, FE `scene-cases.json` 골든 케이스):
- `content_order`: 앞자리 연번 복원(장준용 형식), 역순 입력 → 번호순, 중복·여러 체계·큰 공백은 원래 순서 유지(기존 케이스 유지).
- `split_by_place`: 촬영 시각 없는 사진에서 업로드 순서로 다듬기·경계·최소 구간. 시각 있는 사진 혼합 시 긴 공백 강제 분할 유지. 라벨 80% 미만 → `None`.
- `_run_scene` 본식 경로: 묘사·큰 흐름 호출 0회, 흔들림 완료 전에는 `customer_scenes` 미변경, 흔들림 실패 → 장면 실패.
- 기존 홈스냅·시간 기준 테스트 전부 통과(R10).

FE:
- typecheck, lint, build.
- `tests/e2e/customer/self-customer-upload-queue.spec.ts`에 파일명 정렬 케이스(역순으로 고른 파일이 번호순으로 큐에 들어감).
- `tests/e2e/customer/self-customer-scene-timeline.spec.ts`에 본식 정리 중 배너 문구·완료 뒤 단계 이름 목록(개발용 `?mockAnalysis=`로 상태만 확인).
- 모바일 폭(320~1440px)에서 배너 두 줄·장면 사이드바 이름 길이("원판·단체 기념촬영", "화촉점화·혼주 입장")가 넘치거나 깨지지 않는지 확인.

실측(계획서 §6, 사용자가 직접 실행): 장준용 프로젝트 1차 → 검수 점수와 혼동 행렬 → 목록 조정 → 해군 2차. 결과(2026-10-15, 잠정 정답): 짱쭌 사진 정확도 90.4 → 93.4~94.7%, 장면 15 → 12개(정답 12), 경계 정밀도 43 → 73~90%. 해군 84.0%(계획서 §5.2).

## 8. 배포·되돌리기

- 배포 단위: FE(Vercel)와 clip-service(Railway)를 **같이** 배포한다. BE(FastAPI)·DB는 변경 없음.
- FE만 먼저 나가면: 본식 흔들림 요청에 단계 목록이 실리지만 clip-service가 시각 없는 사진에서 `split_by_place`를 못 돌려 지금과 같은 내용 기준 장면이 나온다(악화 없음, 개선 없음). 흔들림 판정은 단계 라벨을 포함해 저장된다.
- clip-service만 먼저 나가면: FE가 목록을 안 보내므로 동작 변화 없음.
- 본식 단계(`placeMainStages` → `place_main_stages`, 2026-10-15): 옛 clip-service는 이 필드를 무시한다. 새 clip-service가 이 필드 없이 받으면 본식 범위 밖 정리를 하지 않고 카메라를 식 전·본식·식 후 구분 없이 맞춘다.
- 되돌리기: FE 카탈로그 `wedding_ceremony`의 `sceneByStage`를 끄면(또는 이전 배포로 되돌리면) 다음 정리부터 지금 동작으로 돌아간다. 이미 저장된 단계 장면은 다시 정리 전까지 유지된다. clip-service 변경은 홈스냅과 공용이므로 되돌릴 때 홈스냅 테스트를 다시 돌린다.
- 공지: 베타 고객 중 본식 프로젝트가 있으면 "AI 다시 정리를 누르면 단계별 장면으로 바뀌어요"를 안내한다(채널·문구는 출시 때 결정).
