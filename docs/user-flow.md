# 사용자 흐름 (User Flow)

## 작가 추천 편집 (2026-09-18)

원본 업로드 화면은 기존 선택 후 즉시 추천·삭제 동작을 유지하면서 작가 추천 편집을 추가한다. 평상시에는 갤러리 우측 하단에 `작가 추천 N장` 플로팅 버튼으로 표시하며 버튼 주변에서는 사진이 그대로 보인다. 같은 갤러리에서 사진을 눌러 추천에 담거나 빼면 브라우저에 먼저 보관한 뒤 자동 저장한다. 편집 영역은 아래에서 짧게 올라오며 펼쳐지고 최소화할 때는 아래로 내려가며 사라진 뒤 작은 버튼으로 전환된다. 모션 감소 설정에서는 즉시 전환된다. 편집 영역이 펼쳐진 동안에만 선택된 카드에 A 추천 표시가 나타난다. 최소화하면 일반 사진 관리 모드로 돌아가며, 이 상태에서 사진을 선택하면 더보기 메뉴 없이 `선택한 사진 N장 삭제` 버튼만 제공한다. PC 확장 영역은 상단 조작 행과 하단 56px 추천 사진 행으로 나누고 최대 10장을 보여준다. `작가 추천만 보기 / 전체 보기`로 범위를 전환하며 모바일은 기존 높이에서 `추천만 / 전체`로 줄인다. PC는 펼친 상태, 모바일은 접힌 상태로 시작한다. 업로드 중에는 추천 편집을 시작할 수 없다.

추천 변경은 연속 조작을 짧게 묶어 자동 저장한다. `저장 중`에는 계속 사진을 고를 수 있고 최신 변경을 이어서 저장한다. 성공하면 `자동 저장됨`으로 바뀌며 별도 완료·닫기 버튼은 없다. 우측 최소화 버튼으로 일반 사진 관리 모드로 돌아간다. 실패하면 로컬 변경을 보존하고 `다시 저장`을 제공하며, 새로고침해도 복원 후 재시도한다. 저장이 끝나지 않은 동안에는 이탈과 셀렉 요청을 막아 고객에게 이전 구성이 전달되는 것을 예방한다.

유사컷 묶음이 접혀 있고 숨겨진 멤버에 작가 추천 사진이 있으면 대표 카드의 묶음 배지 위에 `A 추천 N장`을 표시한다. 이는 대표 사진 자체의 추천 여부가 아니라 묶음 전체의 추천 현황이며, 묶음을 펼치면 각 사진의 추천 배지로 확인한다.


## 작가 추천 셀렉 (2026-09-15)

- PC 원본 갤러리는 별도 관리 진입점 없이 빈 공간을 드래그해 작업할 사진을 선택할 수 있다. 카드에 마우스를 올리면 좌측 상단에 빈 체크박스를 표시해 단일 선택과 드래그 선택을 발견할 수 있게 한다. 한 장이라도 선택되면 모든 카드의 체크박스와 하단 `고객에게 추천`·`삭제` 작업을 계속 표시하며, 빈 공간을 클릭하면 선택을 모두 해제해 일반 작업 바로 돌아온다. 모바일은 카드 체크박스를 항상 표시하고 길게 누르기도 같은 선택 모드의 보조 동작으로 유지한다. 외부 파일을 끌어오는 업로드는 사진을 선택하지 않은 일반 상태에서 기존 파일 드롭으로 처리한다.
- 별도의 `현재 목록 모두 선택` 버튼은 두지 않는다. PC 갤러리에 포커스가 있을 때 `Ctrl/Cmd + A`는 현재 검색·필터 결과 전체를 선택한다. `Shift + 체크/클릭`은 마지막 기준 사진부터 연속 범위를 추가하고 `Ctrl/Cmd + 클릭`은 해당 사진을 개별 추가·해제한다. 입력 요소와 업로드 중에는 이 단축 조작을 적용하지 않는다.

- PC·모바일 상단의 공용 보기 범위 셀렉터는 `전체 사진 / 추천한 사진`을 바꾼다. 외곽 테두리 없이 현재 범위를 표시하고, 모바일 트리거에서는 공간을 위해 장수를 생략한다. 추천 사진 선택 시 A와 주황 배경을 사용한다. 추천이 0장이어도 업로드 화면의 셀렉터를 유지하며, 기능을 사용하지 않은 브라우저에는 최초 1회 셀렉터에 연결된 안내를 표시한다. `추천한 사진`의 빈 화면은 `전체 사진에서 선택하기`로 복귀시키고 모바일에서는 사진 선택 모드도 함께 연다. PC 원본 업로드에서는 보기 범위·AI 분석·검색·공용 정렬·공용 갤러리/목록 전환을 높이 72px의 한 줄 toolbar에 배치한다. 격자/목록 전환은 PC·모바일 모두 다음 보기로 이동하는 아이콘 하나만 표시한다. 모바일에는 정렬 진입점을 두지 않는다. 원본 정렬은 `파일명순 / 최근 업로드순 / 오래된 업로드순`으로 제한하고 셀렉 결과에만 `코멘트 우선`을 추가한다.
- PC 갤러리는 빈 공간에서 마우스 드래그로 범위를 선택하고 가장자리에서 자동 스크롤한다. Ctrl·Command·Shift를 누른 드래그는 기존 선택에 추가하며 Esc는 진행 중인 드래그를 취소한다. 범위는 검색·필터·유사컷 접힘이 반영된 현재 목록을 기준으로 계산하고, 렌더링되지 않은 행도 포함한다. 선택 후 하단 `선택한 사진 N장 삭제`와 기존 확인창으로 삭제한다. 모바일은 사진을 길게 눌러 선택 모드에 진입한 뒤 탭 선택을 사용하며 `완료`로 복귀한다. 외부 파일 드롭 업로드는 일반 모드에서 제공한다.

- 프로젝트 생성에서는 추천 여부를 묻지 않는다. 원본 업로드 갤러리에서 삭제와 추천이 같은 사진 선택 방식을 사용한다. 사진을 선택하면 하단에 `고객에게 추천`과 `삭제`가 나타나고, 선택한 사진이 모두 추천된 상태면 추천 버튼은 `추천에서 제외`로 바뀐다. 추천 작업을 실행한 뒤 선택은 해제되며 저장된 사진에는 A-CUT A 표시가 남는다. 저장 실패 시 선택을 유지하고 오류를 알린다. 상세 보기에서도 현재 사진을 추천하거나 제외할 수 있다. 추천 사진 결과는 상단 `추천한 사진` 보기에서 확인한다.
- 파일명 검색은 대소문자 무시·한글 NFC 정규화·부분 일치로 현재 목록을 필터링한다. 별도 추천 편집 화면이나 파일명 추가 모달은 없다. 저장한 추천 구성만 셀렉 요청 시 고객에게 공개된다.

- 고객 진입 화면은 추천 장수와 목표 장수의 일치 여부와 관계없이 `작가 추천 확인하기`와 `전체 사진에서 고르기`를 제공한다. 기존 고객 선택이 있으면 `이어서 선택하기`가 주 동작이다. 추천 보기만으로는 체크나 저장 데이터를 변경하지 않는다. A 표시는 작가 추천, 체크는 실제 고객 선택이며 추천 필터와 상세보기에서도 자유롭게 체크를 변경한다.
- 고객 모바일 갤러리는 공간을 차지하는 3분할 탭 대신 상단의 현재 보기 버튼에 `전체 사진 / A 작가 추천 / 내가 선택한 사진`과 장수를 표시한다. 버튼을 누르면 하단 시트에서 보기 범위를 바꾸며, 작가 추천을 보고 있을 때는 주황색 상태와 A 표시로 현재 조건을 알린다. PC는 상시 노출 탭을 유지한다.
- 추천과 기존 선택의 합집합이 목표 이내이면 `이 추천으로 시작하기`(기존 선택이 있으면 `추천 사진도 선택하기`)로 미선택 추천만 한 번에 저장한다. 중복은 한 장으로 계산하며 기존 선택은 유지한다. 부족하면 전체 사진으로 이동해 추가 선택하고 목표를 채우면 선택한 사진 검토로 이동한다. 초과하는 추천은 일괄 적용하지 않으며 고객이 직접 필요한 사진을 고른다. 추천을 해제한 뒤 재접속하거나 필터를 바꿔도 자동으로 재선택하지 않는다.
- PC·모바일의 하단 장수는 항상 실제 고객 선택 합계다. `선택한 N장 확인하기`는 검색·별점·찜·품질·유사컷 묶기를 풀고 선택 사진 전체를 표시한다. 상세보기의 완료 버튼도 같은 검토 목록으로 연결한다. 최종 검토 화면에서만 `보정 요청하기`를 표시하고 `선택한 N장으로 보정을 요청할까요?` 확인창을 거쳐 정확한 목표 장수만 작가에게 전달한다. 저장 중에는 요청할 수 없고 저장 실패는 오류와 체크 복원으로 알린다. 작가 추천은 `preparing`에서만 수정 가능하므로 고객 선택 진행 중 작가 추천 변경은 현재 허용하지 않는다.
- 전체 사진·작가 추천·내가 선택한 사진 필터는 사진 격자 위에 별도의 안내 문구를 표시하지 않는다. 선택 장수와 다음 행동은 헤더·하단 진행 영역에서 확인한다.
- 추천이 없는 기존 프로젝트는 현재의 단일 `사진 선택하기` 흐름을 유지한다. 작가 추천과 고객의 별점·찜·코멘트·선택은 서로 덮어쓰지 않는다.

- `/delivered`는 확정된 최종 납품 아카이브의 검토용 썸네일을 다운로드 정보와 함께 표시한다. PC는 미리보기 영역을 5칸으로 채워 대표 썸네일 4장과 마지막 `+N 더보기` 카드를 표시하고, 모바일은 3칸 중 대표 2장과 더보기 카드를 표시한다. 촬영 정보는 PC와 모바일에서 바로 표시하며 다운로드 기한은 한국 시간 기준 시·분과 고객 화면 공통 D-day 배지를 함께 표시한다. 고객은 썸네일을 눌러 일반 상세보기에서 앞뒤 사진을 확인하고, 사진을 다시 눌러 사진만 보는 집중 확대를 사용할 수 있다. 미리보기는 확인용 축소 이미지이며 원본 크기 최종 보정본은 `최종 보정본 다운로드` 버튼으로 내려받는다. 원본 포함 프로젝트의 촬영 원본 다운로드 버튼은 안내 행의 남은 폭을 채운다. 단일 압축파일은 별도 확인창 없이 바로 다운로드하고, 용량 때문에 여러 파일로 나뉜 경우에만 분할 파일 선택창을 연다.

- `/delivered`는 고객 라이트 완료 화면이다. 촬영일·장소·수령일은 제공된 값만 표시하며, 최종 다운로드 API의 장수·용량·만료일과 공통 D-day, 준비/실패/만료 상태를 버튼 앞에서 안내한다. 원본 포함 프로젝트만 원본 다운로드를 노출한다. ZIP 저장 이후 파일 확인·백업 안내를 제공한다.

## 고객 갤러리 탐색 (2026-09-13)

셀렉 PC의 필터·검색은 툴바에 상시 노출하며 좁은 폭에서는 도구 그룹 단위로 줄바꿈한다. 보정본 목록은 미검토가 남았을 때 하단 버튼으로 첫 미검토 상세에 진입하며, 전체 검토 후 `검토 결과 전달하기`로 기존 확인창과 제출 API에 연결한다. 사진별 판단과 최종 전달은 구분하고, 수령 전용 모드는 기존 수령 완료 동작을 유지한다.

## 재보정 사진 삭제·교체 정책

고객이 검토한 재보정 사진은 삭제하지 않고 교체한다. 현재 또는 이전 V2에 검토 결과·검토 일시가 있으면 삭제 선택 대상과 일괄 창의 삭제 버튼에서 제외하며, 이전 사진·코멘트는 상세 이력으로 보존한다. 새 파일을 다시 교체해도 삭제 잠금은 해제되지 않는다. 최초 고객 검토 전 V2 파일의 삭제와 교체는 허용하고, 고객 확정 사진은 기존처럼 삭제·교체를 금지한다.

## 랜딩의 독립 샘플 체험 (2026-09-11)

- 02 영역은 최초 진입부터 `SAMPLE_SELECTED_PHOTOS`의 원본 4장과 코멘트·별점·찜을 표시한다. 셀렉 확정 전에는 예시를 유지하고, 확정 후 고객이 수정한 선택 결과로 전환한다. 파일명 복사와 CSV는 현재 02에 표시된 결과를 사용한다. 처음부터는 기본 예시로 돌아간다.

- 03 영역은 최초 진입부터 ACUT_0010.jpg 보정본 한 장과 원본 비교 버튼을 표시한다. 등록 후에도 한 장만 표시하고 파일명 탐색 버튼으로 모든 선택 사진을 판단한다. 미검토 사진은 숨겨져 있어도 전체 제출 조건에 포함된다. 원본/보정본을 함께 마운트하고 디코딩 완료 후 비교 버튼을 활성화해, 누르는 동안 opacity만 전환한다. 셀렉 확정 전에도 비교할 수 있다. 실제 검토 판단 체험은 셀렉 확정 → 보정본 등록 예시 보기 이후 현재 선택 결과로 전환한다.

- `/`와 `/landing`의 `LandingStory.tsx`는 고객 셀렉→작가 결과→보정본 등록 예시→고객 검토→완료를 브라우저 메모리 안에서만 체험한다. 고객/작가 API, 실제 프로젝트, 파일 업로드, AI 분석 요청은 호출하지 않는다.
- `SAMPLE_PROJECT.photoCount=13`, `SAMPLE_PROJECT.requiredCount=4`의 샘플을 사용한다. 찜·별점·코멘트는 최종 선택과 별개다. 두 사람의 찜은 역할 전환, AI 유사컷은 제공 사진에서 미리 구성한 여섯 쌍으로 시연한다. 확정 후 선택 편집을 잠그고 동일 파일명·사진·코멘트를 작가 결과로 전달한다.
- 이전 구성(아래 01 갤러리 개선으로 대체): 유사컷은 기본적으로 접힌 6개 표지와 단독 사진 1장으로 표시한다(`grouped=true`, `expandedGroups=[]`). 선택 사진이 있는 묶음은 선택 사진을 표지로 사용한다. 각 표지의 `2장 펼치기`로 해당 묶음만 펼치고 다시 접을 수 있으며, 전체 사진 보기에서는 13장을 표시한다. 펼침·접힘은 사진별 선택·찜·별점·요청을 보존한다. 사진 그리드는 데스크톱 최대 440px, 모바일 최대 350px(`story.css`의 `.as-photo-grid`) 내부 스크롤로 랜딩 높이를 제한한다. 처음부터는 묶음을 다시 접는다.
- 작가 결과의 복사·CSV 다운로드는 현재 샘플 선택을 사용한다. CSV 코멘트는 따옴표 이스케이프 및 수식 접두어 방어를 적용한다. 실제 보정은 외부 편집 도구에서 작가가 수행함을 설명하고, 데모의 등록 버튼은 선택한 사진에 연결된 보정본을 표시한다.
- 사진별 검토 판단을 모두 마쳐야 제출할 수 있고 재보정에는 사유가 필요하다. 요청 후 수정본 등록 예시를 누르면 요청 사진만 미검토로 되돌리고 확정 사진은 유지한다. 데모는 재보정 한 번을 제공하며 서비스의 횟수 정책과 구분한다. 원본 비교는 포인터 또는 키보드로 누르는 동안 동일 파일명의 원본을 표시한다. 기본 선택 0001·0006·0010·0013은 제공 보정본을 표시한다. 나머지는 준비 중이며 유사컷으로 대체하지 않는다.
- 완료 상태는 아래 가상 프로젝트 카드에도 반영된다. 처음부터 버튼은 선택·찜·별점·코멘트·검토·메시지를 초기화한다. 상하단·요금 영역의 “무료 시작하기” CTA는 클릭 시 세션을 확인하고, 비로그인 상태이면 로그인 모달을 연다. 로그인 후에는 작가 대시보드로 연결되며 기존 세션이 있으면 바로 이동한다. 샘플 스크롤은 “고객 셀렉 체험하기” 보조 링크로 제공한다. 랜딩 진입 시 인증 조회는 하지 않으며 이용 조건은 `SAMPLE_PLAN_LIMITS` 가상 수치를 표시한다. 가이드·베타 링크는 prefetch 없이 명시적 이동만 제공한다. 히어로는 휴대폰 고객 셀렉 → 사진별 요청 입력·저장 → 작가 결과 확인 → 보정본 한 장 업로드를 20초 무음 WebM/MP4로 반복 재생한다. 작가 결과는 실제 셀렉 갤러리와 사진 아래 코멘트를 사용하며 별도 오른쪽 요청 패널은 표시하지 않는다. 모바일 화면 폭에서는 전용 세로 영상과 poster를 사용한다. 히어로와 03 검토 영상은 공통 `LandingVideo`를 사용하며 움직임 축소 설정에서도 무음 자동재생을 시도한다. 자동재생 거절·미디어 오류 시 poster와 수동 재생 버튼을 제공한다. 실제 고객 사진은 사용하지 않는다. 히어로 영상은 샘플 10장 중 3장을 선택하는 별도 시연이고 아래 체험의 13장/4장 상태와 독립적이다.

# Part 1. 고객 흐름

## 1. 공유 링크 최초 접속

- **시작 조건**: 작가가 공유한 `https://.../c/{access_token}` 링크를 클릭. 브라우저에 해당 프로젝트의 쿠키가 없는 상태.
- **사용자가 수행하는 단계**: 링크 클릭 → (PIN 유무에 따라 자동 분기).
- **프론트엔드 라우트**: 고객 미들웨어가 `/c/[token]` 루트와 하위 경로를 먼저 인증한 뒤, 루트 서버 컴포넌트가 상태에 따라 `/locked`, `/confirmed`, `/delivered`로 redirect하거나 `InvitePageWrapper`/`InvitePageClient`를 렌더.
- **호출되는 API**: 미들웨어가 Supabase에서 현재 `projects.access_pin`을 조회하고, 쿠키 서명이 토큰뿐 아니라 현재 PIN 상태와도 일치하는지 확인한다. 이후 서버 컴포넌트가 요청 단위 캐시된 `getProjectByTokenCached()`로 프로젝트 상태와 서명 쿠키를 확인하고, 클라이언트 렌더 후 `GET /api/c/photographer?token=...`로 작가 프로필을 표시한다.
- **성공 시 기대 결과**:
  - PIN 없는 프로젝트는 현재 요청에서 서명 쿠키를 발급하고 추가 redirect 없이 계속 렌더한다. PIN 보호 프로젝트만 `/c/[token]/pin?from=...`으로 이동한다.
  - `editing`/`editing_v2` → `/locked`, `confirmed` → `/confirmed`, `delivered` → `/delivered`로 서버에서 즉시 이동한다.
  - `selecting`은 Figma `#56108` 기반 라이트 인트로를 표시한다. 작가가 지정한 `cover_photo_id`의 preview를 모바일 전체 폭 hero로 사용하고 중앙 기준으로 잘라 표시한다. 미지정 또는 삭제된 경우 첫 사진으로 폴백하며 presign 실패 시 light brand placeholder를 유지한다. 작가 프로필, 고객명, 전체 사진 수, 필수 선택 수, 선택 마감일/D-day, `사진 N장 셀렉하기` CTA를 노출한다. 소개글·인스타그램·포트폴리오 중 하나라도 등록돼 있으면 사진 위 작가 정보에 `작가 소개` 진입점을 표시하고, PC에서는 작가 정보 옆 팝오버, 모바일에서는 하단 시트로 등록된 항목만 보여준다. 외부 링크는 HTTP(S) 주소만 새 탭으로 연다. D-day는 3일 이내 주황색, 당일·초과는 빨간색으로 강조하지만 서버 차단 조건은 아니므로 지난 경우에도 `D+N`으로 표시하고 CTA를 막지 않는다. 원본 포함 프로젝트는 같은 하단 action 영역에서 `원본 다운로드 받기`로 기존 다운로드 modal을 연다. PC는 viewport 전체를 대표 사진과 안내/CTA로 나누는 split composition을 사용한다.
- **실패 및 경계 상황**:
  - 존재하지 않는 `access_token` → `project`가 `null` → "존재하지 않는 초대 링크입니다 / URL을 다시 확인해주세요" 화면(`InvitePageClient.tsx`).
  - `project.status === "preparing"`(작가가 아직 초대 링크를 활성화하지 않음)인 경우 정확히 어떤 화면이 보이는지는 코드상 명시적 분기가 없어 소개 화면이 그대로 노출될 것으로 보임 — 사진이 없는 상태에서의 UX는 **확인 필요**(직접 브라우저 확인 권장).
- **관련 권한/인증 조건**: 없음(토큰만 있으면 접근 가능, PIN이 있으면 PIN 필요).
- **QA에서 확인해야 할 항목**:
  - 존재하지 않는 토큰, 형식이 이상한 토큰(공백/특수문자) 접근 시 에러 화면과 콘솔 에러 여부.
  - `preparing` 상태(업로드 미완료) 프로젝트 링크에 고객이 실수로 접근했을 때 화면.
  - `delivered` 상태 프로젝트에 이 경로로 접근 시 리다이렉트가 항상 동작하는지(딥링크 포함).

## 2. PIN이 있는 프로젝트 인증

- **시작 조건**: `projects.access_pin`이 설정된 프로젝트 링크에 쿠키 없이 접근.
- **사용자가 수행하는 단계**: 링크 접속 → 자동으로 `/pin`으로 이동 → 화면 숫자 키패드 또는 물리 키보드로 4자리 숫자 입력(4번째 자리 입력 시 기존과 같이 자동 제출, 하단 `확인` CTA로도 제출 가능). reset은 전체 입력을, backspace는 마지막 숫자를 지운다.
- **프론트엔드 라우트**: `/c/[token]/pin` (`pin/page.tsx` 서버 컴포넌트 + `PinForm.tsx` 클라이언트).
- **호출되는 API**: `POST /api/c/verify-pin` `{ token, pin }`.
- **성공 시 기대 결과**: 200 `{success:true}` + `Set-Cookie: pin_verified_{token}`(HttpOnly, 현재 PIN 상태를 포함한 서명, 24h) → `window.location.href = from`으로 **전체 페이지 이동**하여 원래 목적지(기본값 `/c/[token]`)로 이동. PIN을 설정·변경·삭제하면 이전 PIN 상태로 발급된 쿠키는 즉시 무효가 된다. (과거 `router.replace`를 쓸 때 목적지 페이지가 "INVALID_TOKEN"을 표시하던 버그가 있었고, 전체 페이지 이동으로 수정된 이력이 있음 — 관련 회귀 테스트 `tests/e2e/customer/pin-auth.spec.ts` U1.)
- **실패 및 경계 상황**:
  - PIN 불일치 → 401 `{success:false, remaining}`, 4자리 표시를 비우고 네 line을 빨간색으로 바꾼 뒤 "비밀번호가 올바르지 않습니다" 표시.
  - 1분 내 5회 이상 시도 → 429 `{locked:true, retryAfterSeconds}`, 카운트다운 표시 + 입력 비활성화, 카운트다운 종료 시 자동 재활성화.
  - 네트워크 오류 → "오류가 발생했습니다. 다시 시도해주세요." 표시.
- **관련 권한/인증 조건**: `pin_attempts` 테이블 기준 토큰당 1분 5회 rate limit(로그인 계정과 무관, IP 기록만 함 — IP 자체로 차단하지는 않음).
- **QA에서 확인해야 할 항목**:
  - 정답 PIN 입력 후 새로고침 없이 목적지 페이지가 실제 데이터로 렌더링되는지(과거 회귀 버그).
  - 5회 락아웃 → 카운트다운 종료 후 실제로 재시도가 되는지.
  - 모바일 뷰포트에서 자동 포커스 이동/자동 제출이 정상 동작하는지.

## 3. PIN이 없는 프로젝트 접속

- **시작 조건**: `projects.access_pin === null`인 프로젝트 링크에 쿠키 없이 접근.
- **사용자가 수행하는 단계**: 링크 클릭만 하면 됨(입력 없음).
- **프론트엔드 라우트**: 사용자가 요청한 `/c/[token]` 또는 하위 경로를 그대로 유지한다. 미들웨어가 인증을 완료하므로 `/pin`을 경유하지 않는다.
- **호출되는 API**: 별도 브라우저 API 호출 없음. 미들웨어가 Supabase REST로 `access_pin`만 확인하고 현재 응답에 쿠키를 설정한다. `/api/c/auto-verify`는 `/pin` 직접 접근 호환용 fallback으로만 유지한다.
- **성공 시 기대 결과**: PIN 입력 화면과 redirect 왕복 없이 원래 목적지를 바로 렌더하고 현재의 `PIN 없음` 상태에 묶인 `pin_verified_{token}` 쿠키를 발급한다(24h).
- **실패 및 경계 상황**: 프로젝트를 찾지 못한 루트 링크는 기존 `INVALID_TOKEN` 화면에서 처리한다. 조회 실패 또는 PIN이 설정된 하위 경로는 fail-closed로 `/pin` 이동을 유지한다.
- **관련 권한/인증 조건**: 없음(링크만 알면 접근 가능 — 설계상 의도된 동작으로 보임).
- **QA에서 확인해야 할 항목**: PIN 없는 프로젝트를 먼저 연 고객 브라우저에서 작가가 PIN을 추가한 뒤 새로고침하면 즉시 PIN 입력 화면으로 이동하는지(회귀 테스트 `pin-auth.spec.ts` M4).

## 4. 잘못된 PIN 입력 후 재입력

- **시작 조건**: PIN 입력 화면에서 최소 1회 오답 상태(락아웃 전).
- **사용자가 수행하는 단계**: 오답 입력(자동 제출) → 에러 확인 → 입력칸이 비워지고 포커스가 첫 칸으로 복귀 → 올바른 PIN 재입력.
- **프론트엔드 라우트**: `/c/[token]/pin` (동일 페이지 내에서 처리, 페이지 이동 없음).
- **호출되는 API**: `POST /api/c/verify-pin`을 오답 1회 + 정답 1회, 총 2회 호출(각각 `pin_attempts`에 기록됨).
- **성공 시 기대 결과**: 정답 제출 시 §2와 동일하게 정상 인증 및 목적지 이동.
- **실패 및 경계 상황**: 오답 후 남은 시도 횟수(`remaining`)가 화면에 노출되지는 않음(에러 문구는 고정 텍스트) — `remaining` 값은 응답 바디에는 있지만 UI에서 사용되는지는 **확인 필요**(코드상 `PinForm.tsx`가 `data.remaining`을 렌더링에 사용하지 않는 것으로 보임).

- **QA에서 확인해야 할 항목**: 오답을 4회까지 반복한 뒤 5번째에 정답을 입력하면 정상 통과하는지(락아웃 임계값이 "5회 이상"이라 정답 시도도 카운트에 포함되는지 경계값 확인).

## 5. 인증 후 갤러리 진입

- **시작 조건**: PIN 인증 완료(또는 PIN 없음) + `projects.status === "selecting"` (또는 `preparing`).
- **사용자가 수행하는 단계**: 초대 화면 또는 직접 링크에서 갤러리로 이동.
- **프론트엔드 라우트**: `/c/[token]/gallery` (`GalleryPageClient.tsx`).
- **호출되는 API**: `GET /api/c/photos?token=...` (via `SelectionContext`) — 프로젝트/사진/기존 선택/`photo_groups` 반환. 그리드 카드의 실제 썸네일 이미지는 `photos.r2_thumb_url`을 직접 쓰지 않고, `GET /api/c/presign-thumbs?token=...&photoIds=...`(최대 200장/요청, FastAPI `/api/storage/presign` 프록시)로 발급받은 presigned GET URL을 사용한다 — R2 key 자체는 응답에 노출되지 않는다. 최초 가상화 범위는 debounce 없이 즉시 요청하고 이후 빠른 스크롤 범위만 80ms 안정화하며, PIN 인증에서 확인한 프로젝트 ID를 썸네일 소유권 조회에 재사용한다(§8.1·§10 upload-flow.md 참고, 과거 문서는 "r2_thumb_url을 그대로 사용"으로 잘못 서술돼 있었음, 2026-08-06 정정).
- **성공 시 기대 결과**: Figma `#55882` 기반 모바일 갤러리는 2열로 시작한다. 모바일 툴바의 그리드 아이콘을 누르면 2/3/4열을 순환하며 갤러리만 reflow한다. 전환 전 화면 중앙 사진을 앵커로 유지하고 토큰별 밀도를 탭 세션에 저장한다. 2열은 파일명·별점·색상을 함께 보여주고 저장된 코멘트가 있는 사진에는 하단 우측에 주황색 말풍선 아이콘을 표시한다. 코멘트 본문은 상세 뷰어에서 확인한다. 3열부터 정보를 점진적으로 축약하고 4열은 image-only로 표시한다. Figma `#55883`에 따라 `전체/선택됨` scope dropdown, 별점 단일·색상 복수 선택 bottom sheet, 활성 조건 badge/removable chip, 필터 결과 없음 화면을 제공한다. 별점은 기존 계약처럼 해당 점수 이상, 여러 색상은 OR로 필터링한다. 선택 수가 필수 수와 같으면 `셀렉 확정하기`로 기존 확정 modal/API를 실행한다. 이미 저장된 선택/별점/코멘트는 그대로 유지한다. 작가가 "유사컷 분석"을 실행해 완료된 프로젝트라면, 흔들림/눈감음 의심 사진에 경고 배지(⚠, 카드 우상단)가 표시됨 — **정보성 참고용이며 선택/확정을 막지 않음**. **(2026-07-28 베타 전환)** 이 배지는 OpenCLIP 파이프라인이 채우던 `blur_variance` 등 컬럼 기반인데, 유사컷 분석 버튼이 Gemini로 전환되며 신규 분석에서는 더 이상 이 컬럼들이 채워지지 않는다 — 배지 UI 코드는 남아있지만 과거(전환 이전) OpenCLIP으로 분석된 프로젝트에서만 실제로 보이고, 신규/재분석 프로젝트에는 나타나지 않는다. 분석 완료 이후 고객이 갤러리를 처음 여는 시점 기준으로만 반영되고, 이미 갤러리를 열어둔 상태에서 작가가 재분석하면 새로고침 전까지 배지가 갱신되지 않음. 같은 조건(분석 완료된 프로젝트)에서는 PC filter bar와 모바일 toolbar에 "유사컷 묶어보기"가 노출된다. 모바일은 필터와 구분된 `Layers + 유사컷 + 그룹 수` 보기 모드 버튼이며 최초 1회 사용 안내를 표시한다. 이 토글은 `photo_groups`/`similarity_group_id`를 그대로 읽고 `grouped=1` URL 상태로 뷰어까지 이어지므로 Gemini 전환 이후에도 동일하게 동작한다. **(2026-07-30 UX 개선)** 켜면 각 그룹의 "표지" 사진 1장만 보이고 나머지 멤버는 숨겨진다 — 표지는 그룹 내 선택된 사진이 없으면 내부적으로 계산된 기본 표지(구 "대표컷", 화면에는 이 개념이 노출되지 않음)이고, 1장 이상 선택돼 있으면 선택 개수와 무관하게 항상 "선택된 사진 중 원래 촬영/파일 순서가 가장 앞선 사진"이 표지가 된다. 배지는 항상 `+N`(표지 외에 접힌 사진 수, 선택 개수와 무관하게 고정) 형태이고, 그룹 내 선택이 1장 이상이면 `+N · M/전체 선택`처럼 선택 수를 함께 표시한다. 펼치면 항상 원래 촬영/파일 순서(orderIndex)대로 나열되며, 사진을 선택/해제해도 그 순서나 그룹 펼침/접힘 상태는 전혀 바뀌지 않는다(그룹 내 여러 장을 선택해도 자동으로 펼쳐지거나 풀리지 않음) — 이 토글은 고객이 선택 가능한 사진의 화면상 가시성에 직접 영향을 준다.
- **실패 및 경계 상황**:
  - `project.status === "preparing"` → `/c/[token]`으로 되돌림(`GalleryPageClient.tsx:150`).
  - `project.status === "confirmed"` → `/c/[token]/confirmed`로 이동.
  - `project.status === "editing"` → `/c/[token]/locked`로 이동.
  - `project`가 끝내 `null`이면(§BUG-001 계열) "INVALID_TOKEN" 표시 — 정상 흐름에서는 인증 후 전체 페이지 이동으로 재발생하지 않음(§2 참고).
- **관련 권한/인증 조건**: PIN 쿠키 필요(미들웨어가 `/c/:token` 루트와 `/c/:token/:path+`를 모두 보호).
- **QA에서 확인해야 할 항목**: 사진 수가 많은 프로젝트(수백 장)에서 최초 썸네일 표시 시간과 빠른 스크롤 후 빈 placeholder 회복 시간. 가상 스크롤은 실제로 적용되어 있음(`GalleryPageClient.tsx`가 `@tanstack/react-virtual`의 `useWindowVirtualizer`로 행 단위 가상화, 화면+overscan 범위만 DOM에 렌더). 화면 근처 진입은 `IntersectionObserver`가 제어하고 허가된 이미지는 12개 동시 큐에서 `eager`로 시작하므로 별도의 native lazy 지연을 만들지 않는다. iOS Safari/Android Chrome에서 2→3→4→2열 버튼 순환, 세션 저장, 열 전환 후 중앙 사진 유지도 확인한다.
- **갤러리 카드 경계 규칙**: 모바일 그리드 버튼으로 전환하는 2~4열은 모두 고객/작가 공통 `PhotoThumbnailFrame`을 사용한다. 기본 사진에는 검정·회색 외곽선을 표시하지 않고 선택 또는 펼친 그룹 상태만 2px 주황색 inset으로 확인한다.

## 6. 사진 조회 및 상세 보기

- **시작 조건**: 갤러리 진입 완료, `status === "selecting"`.
- **사용자가 수행하는 단계**: 사진 클릭 → 전체화면 뷰어 진입 → 좌우 이동/ESC로 갤러리 복귀.
- **프론트엔드 라우트**: `/c/[token]/viewer/[photoId]` (`src/app/c/[token]/viewer/[photoId]/page.tsx`).
- **호출되는 API**: `SelectionContext`의 기존 데이터 사용(추가 목록 조회 없음) + 대형 프리뷰 이미지는 `GET /api/c/presign-preview?photoIds=...`로 현재·인접 사진의 presigned URL을 최대 5장까지 배치 발급받는다(FastAPI `/api/storage/presign` 경유). PC는 현재 기준 이전 1장·다음 2장, 모바일은 양옆 1장을 실제 이미지 decode까지 미리 시작하고, 발급 URL은 만료 전까지 재사용한다. 데이터 절약 모드에서는 현재 사진만 요청한다.
- **성공 시 기대 결과**: 원본 대비 축소된 프리뷰(1200px) 표시, 별점/색상/코멘트/선택 토글 UI 노출. 모바일은 Figma `#56109` 기준으로 파일명과 선택 토글 앱바 → 별점·색상 → 확대 가능한 이미지 → 유사컷 pill → 소형 필름스트립 → 코멘트 순서로 표시한다. 필름스트립은 첫 사진을 왼쪽 `20px`, 마지막 사진을 오른쪽 `20px`에 맞추고 중간 사진만 스크롤 가능한 범위에서 중앙 정렬한다. 유사컷 pill을 열면 필름스트립이 그룹 멤버로 전환되고, 코멘트 입력 시 키보드 위 white composer를 연다. PC의 기존 위치·진행률 중심 헤더와 하단 평가 구조는 유지한다.
- **실패 및 경계 상황**: presign 호출이 실패하거나 아직 응답 전이면 현재 공개 R2 전환 기간에는 `r2_preview_url`(없으면 썸네일)을 즉시 표시한다. 존재하지 않는 `photoId`는 "사진을 찾을 수 없습니다" 안내와 갤러리 복귀 링크를 표시한다.
- **관련 권한/인증 조건**: PIN 쿠키(미들웨어 보호 대상).
- **QA에서 확인해야 할 항목**: 방향키/스와이프로 이전·다음 이동, 마지막/첫 사진에서 경계 동작, 이미지 우클릭/드래그 저장 방지(`NEXT_PUBLIC_BLOCK_VIEWER_IMAGE_DOWNLOAD` 옵션) 동작 여부.

### 6-1. 유사컷 그룹 skip 내비게이션 (뷰어)

갤러리에서 "유사컷 묶어보기" 토글을 켠 상태로 사진을 클릭하면, 이 상태가 뷰어 URL에 `?grouped=1`로 전달된다
(`GalleryFilterState.groupedView` → `buildFilterQueryString`, `src/lib/gallery-filter.ts`). 뷰어는 이 파라미터를
`parseFilterFromSearchParams`로 읽어 그룹핑을 활성화한다(`groupingActive` — 파일명/품질 필터가 켜져 있으면 그룹 접기보다
우선하므로 자동으로 비활성화됨, 갤러리와 동일 규칙).

**(2026-07-30 UX 개선)** 그룹의 "표지(front)" 개념과 펼침 상태 관리가 다음과 같이 바뀌었다:

- **필름스트립/좌우 이동/스와이프는 표지 사진(+미소속 사진) 단위로만 동작한다** — 그룹의 다른 멤버는 목록에서
  제외되므로 "다음/이전"이 항상 그룹을 건너뛴다(`src/lib/photo-groups.ts`의 `filterToGroupFrontPhotos`/`getGroupFrontPhotoId`
  사용, 갤러리와 공용). 표지는 그룹 내 선택된 사진이 없으면 내부 기본 표지(구 "대표컷", 화면에 노출되지 않음)이고,
  1장 이상 선택돼 있으면 선택 개수와 무관하게 항상 "선택된 사진 중 원래 촬영/파일 순서(orderIndex)가 가장 앞선 사진"이다.
- 표지 하단에 그룹이 있음을 암시하는 힌트(PC: `◧ 유사컷 N장 ▾` pill, 모바일: 이미지 아래 장수 pill)가 나타나며,
  클릭/탭하면 나머지 멤버가 펼쳐진다 — PC는 필름스트립 위 미니 스트립, 모바일은 동일 위치의 필름스트립이 그룹 멤버 목록으로 전환된다.
  펼쳐진 멤버는 **항상 원래 촬영/파일 순서(orderIndex)대로 나열**되고, 멤버를 클릭해 미리보기를 전환하거나 다른
  사진을 선택/해제해도 이 순서나 펼침 상태는 전혀 바뀌지 않는다(그룹 내 여러 장을 선택해도 자동으로 펼쳐지거나
  풀리지 않음 — 셀렉 상태와 펼침 상태는 완전히 분리되어 있다).
- 메인 필름스트립에서 펼쳐진 그룹의 표지 썸네일에는 오렌지 링(`.fs-thumb.group-expanded`)이 표시된다.
- **펼침 상태는 그룹(groupId)별로 세션 내내 기억된다**(`groupExpandStateRef`): 그룹에 처음 진입할 때만
  "지금 보는 사진이 표지가 아니면 1회 자동으로 편다"를 판단하고, 그 이후로는 사용자가 펼치기/접기 버튼으로
  명시적으로 바꾸기 전까지 그 상태를 유지한다 — 다른 그룹이나 미소속 사진으로 이동했다가 다시 돌아와도
  이전에 접었던 그룹은 계속 접힌 채로 남는다. 그룹핑 토글을 껐다가 다시 켜면 모든 그룹의 기억이 초기화되어
  다시 "새 진입"으로 취급된다. 미소속 사진으로 이동하면 열려있던 패널 UI는 닫히지만(펼침 여부 자체는 그
  이전 그룹의 기억에 그대로 남아있음), 그룹이 없는 사진에는 애초에 패널이 뜨지 않는다.
- 모바일 그룹 필름스트립이 열린 상태에서도 이미지 swipe로 다음 그룹 표지로 이동할 수 있고, 썸네일 탭으로 그룹 내부 사진을 직접 미리 볼 수 있다.
- `?grouped=1`이 없으면(토글 OFF 상태에서 진입, 또는 구형 링크) 기존처럼 전체 사진을 낱장으로 순회하는 동작이 그대로 유지된다.

## 7. 사진 선택과 선택 취소

- **시작 조건**: 갤러리 또는 뷰어에서 `status === "selecting"`.
- **사용자가 수행하는 단계**: 사진(또는 체크박스) 클릭으로 선택 토글.
- **프론트엔드 라우트**: `/c/[token]/gallery`, `/c/[token]/viewer/[photoId]` (둘 다 `SelectionContext.toggle()` 사용).
- **호출되는 API**: `POST /api/c/selections` `{ token, project_id, photo_id, is_selected }` — `rating`/`color_tag`/`comment`는 이번에 안 바뀌면 body에 아예 포함하지 않는다(서버가 생략된 필드는 건드리지 않음). fire-and-forget(응답을 기다리지 않고 UI는 즉시 갱신).
- **성공 시 기대 결과**: 헤더의 "SELECTED Y / N" 카운트 갱신, `selections` 테이블에 upsert. PC 뷰어는 사진의 오렌지 체크 배지와 `✓ 선택됨 · Y / N` CTA로 표시한다. 모바일 상세는 너비가 고정된 우측 앱바의 orange outline `선택`이 orange fill·white check `선택됨` pill로 바뀌고, 필름스트립에도 갤러리와 동일한 orange square check가 나타나 상태 변경을 즉시 확인할 수 있다. 필름스트립의 현재 사진은 white border로 표시해 선택 상태와 구분한다. 선택 시 pill과 square check가 짧게 pop되고 실제 사진 경계에 `300ms` orange flash가 나타나며, 해제 시에는 check만 fade-out한다. `prefers-reduced-motion`에서는 이 모션을 생략한다. 실제 선택/해제가 가능한 탭에는 지원 브라우저에서 `10ms` 진동 피드백을 제공하며, 목표 장수를 채워 추가 선택이 차단된 탭과 진동 API 미지원 환경에서는 진동하지 않는다.
- **실패 및 경계 상황**:
  - 이미 N장을 채운 상태에서 새 사진을 선택하려 하면 **클라이언트에서 차단**(요청 자체가 서버로 가지 않음) — 이미 선택된 사진을 해제하는 것은 언제나 가능.
  - 차단된 탭에는 `N장을 모두 선택했어요`와 해제 방법을 안내하는 snackbar를 표시한다. `선택한 사진 보기`를 누르면 `선택됨` scope로 이동하며, 선택 수·진행 영역의 orange pulse와 지원 브라우저의 짧은 거절 진동으로 탭이 인식됐음을 피드백한다. snackbar는 5초 후 자동으로 닫히고 선택 수는 N을 유지한다.
  - **서버 측에는 N장 제한 검증이 없음** — 클라이언트 로직을 우회해 N장 넘게 저장을 시도하면 `selections` 테이블에는 들어갈 수 있으나, `/api/c/confirm`에서 개수 불일치로 최종 확정은 거부됨.
  - `status`가 `selecting`/`preparing`이 아니면 서버가 403 반환(예: 이미 확정된 후 뒤늦은 요청).
- **관련 권한/인증 조건**: PIN 쿠키, `checkPinAuth` + `validateTokenAndProject`.
- **QA에서 확인해야 할 항목**: 빠른 연속 클릭(더블 클릭) 시 상태 깜빡임 여부, 네트워크 지연 중 여러 번 클릭했을 때 최종 상태 일관성, 새로고침 시 선택 상태가 서버 값과 일치하는지. 선택 직후 PC·모바일의 pill/CTA 상태가 올바르게 전환되는지도 확인한다. **여러 브라우저(동일 토큰)에서 서로 다른 사진/필드를 동시에 편집해도 서로의 값을 지우지 않는지**(2026-07-28 수정 — §8, 부록 참고).

## 8. 별점 및 코멘트 저장

- **시작 조건**: 뷰어 또는 갤러리 카드에서 `status === "selecting"`.
- **사용자가 수행하는 단계**: 별점(1~5) 클릭, 색상 태그 선택, 코멘트 입력. 뷰어의 코멘트는 입력이 600ms 멈추면 자동 저장되며, 포커스 아웃·저장 버튼·다른 사진으로 이동할 때도 즉시 저장을 시도한다. PC는 입력창 위에 저장 상태를 표시하고, 모바일 composer는 저장 중 상태와 실패 시 재시도 동작을 간결하게 표시한다.
- **프론트엔드 라우트**: `/c/[token]/viewer/[photoId]` (주 입력처), `/c/[token]/gallery`(카드 오버레이에서도 가능할 수 있음, **확인 필요**).
- **호출되는 API**: `POST /api/c/selections` — 이번에 실제로 바뀐 필드(`rating`/`color_tag`(직렬화됨)/`comment` 중 해당하는 것)만 body에 포함하고 나머지는 생략, `is_selected`도 생략(서버가 기존 값을 그대로 보존). 예: 색상칩만 클릭하면 `color_tag`만 전송되고 `rating`/`comment`는 body에 없음.
- **성공 시 기대 결과**: 별점/태그/코멘트가 즉시 UI에 반영되고 서버에도 저장됨. PC 코멘트는 완료 후 2초간 `✓ 저장됨`을 보여준 뒤 `자동 저장` 안내로 돌아가고, 모바일은 저장된 코멘트를 orange outline 2줄 preview로 보여준다.
- **실패 및 경계 상황**: 코멘트 저장 요청이 실패하면 입력한 내용을 유지하고 `저장 실패 · 다시 시도`를 표시한다. 다시 시도는 같은 코멘트를 재전송한다. (과거엔 안 바뀐 필드까지 로컬 캐시 값 그대로 재전송해서, 동시에 다른 세션이 그 사이 저장한 값을 덮어쓰는 데이터 유실 버그가 있었음 — 2026-07-28 수정, §11/부록 참고.)
- **관련 권한/인증 조건**: PIN 쿠키, `status`가 `selecting`/`preparing`이어야 함.
- **QA에서 확인해야 할 항목**: 특수문자·이모지·매우 긴 코멘트 입력, 600ms 자동 저장·blur·Enter·사진 이동 시 저장, 저장 중/완료/실패 상태가 PC·모바일에서 올바르게 전환되는지, 코멘트 저장 실패 시(네트워크 끊김) 입력값을 유지한 채 재시도할 수 있는지, 별점을 준 뒤 선택을 해제해도 별점이 유지되는지. **여러 브라우저(동일 토큰)에서 서로 다른 필드를 동시에 편집해도 유실되지 않는지**(A가 별점, B가 색상칩을 거의 동시에 저장 → 둘 다 남아있어야 함).

## 9. 새로고침과 새 탭에서 상태 유지

- **시작 조건**: PIN 인증 완료 상태(쿠키 존재).
- **사용자가 수행하는 단계**: 브라우저 새로고침, 또는 같은 링크를 새 탭에서 열기.
- **프론트엔드 라우트**: 접근하던 라우트 그대로.
- **호출되는 API**: 페이지 재마운트에 따라 `GET /api/c/photos` 등이 다시 호출됨(쿠키가 브라우저 프로필 단위로 공유되므로 새 탭에서도 동일 쿠키 사용).
- **성공 시 기대 결과**: 재인증 없이 동일 화면 유지, 선택/별점/코멘트는 서버에 저장된 값 기준으로 다시 로드됨(클라이언트 로컬 상태를 별도로 캐시하지 않음). **갤러리(`/c/[token]/gallery`)의 필터 상태(선택됨 탭/별점/색상/정렬/파일명 검색/흔들림·눈감음 필터/유사컷 대표이미지 적용 토글)는 URL 쿼리에 반영되어 새로고침·뒤로가기 후에도 유지된다** — 필터를 바꿀 때마다 `router.replace`로 URL만 갱신(히스토리에 새 엔트리를 쌓지 않음), 마운트 시 URL에서 1회 복원. 뷰어와 동일한 `GalleryFilterState`/`parseFilterFromSearchParams`/`buildFilterQueryString`(`src/lib/gallery-filter.ts`)을 재사용.
- **새로고침 없이도 다른 세션의 변경사항이 반영됨(2026-07-28 추가)**: `status`가 `selecting`/`preparing`인 동안 `SelectionContext`가 5초 간격으로 선택/별점/색상/코멘트만 폴링해 화면에 반영한다(사진 목록·필터는 폴링 대상 아님). 완전한 실시간(WebSocket 등)은 아니라서 최대 폴링 주기(탭이 백그라운드면 그동안 정지, 포그라운드 복귀 시 즉시 1회 재조회)만큼 지연될 수 있다.
- **동시 선택 제한**: 여러 세션이 동시에 서로 다른 사진을 선택해도 서버가 프로젝트 단위로 요청을 직렬화하고 목표 장수 초과 요청을 거부한다. 거부된 세션은 낙관적으로 표시한 체크를 되돌리고 `다른 참여자가 먼저 목표 장수를 채웠어요`를 표시하며, 다음 폴링에서 양쪽 화면이 같은 선택 상태로 수렴한다. 서로 다른 참가자의 찜 색상은 사진별 원자적 add/remove로 모두 보존한다.
- **실패 및 경계 상황**: 쿠키의 서명 타임스탬프가 24시간을 넘으면 새로고침 시 `/pin`으로 다시 리다이렉트됨(§10 참고). 시크릿 모드/다른 브라우저에서는 쿠키가 공유되지 않아 재인증 필요. PIN 쿠키가 아직 없는 상태로 쿼리 파라미터가 붙은 링크(필터/그룹 상태 포함)에 처음 접근하면, `/pin` 인증 왕복 후에도 원래 쿼리스트링이 그대로 보존되어 목적지 URL에 복원된다(`src/middleware.ts`가 리다이렉트 시 `pathname`뿐 아니라 `search`까지 `from` 파라미터에 함께 실어 보냄 — 과거엔 쿼리스트링이 유실되는 버그가 있었음, 회귀 테스트: `tests/e2e/customer/pin-auth.spec.ts` M3).
- **관련 권한/인증 조건**: 쿠키는 `path: "/"`, `sameSite: lax`로 발급되어 같은 브라우저의 모든 탭에서 공유됨.
- **QA에서 확인해야 할 항목**: 새로고침 직후 로딩 중 상태에서 조작 시 에러 여부, 다른 프로젝트 탭을 동시에 열었을 때 쿠키 이름이 토큰별로 분리되어 있어 서로 간섭하지 않는지.

## 10. 만료되거나 잘못된 링크 접근

- **시작 조건**: (a) 존재하지 않는 토큰, (b) 형식은 맞지만 DB에 없는 토큰, (c) 24시간이 지나 만료된 PIN 쿠키, (d) 변조된 쿠키.
- **사용자가 수행하는 단계**: 잘못된/오래된 링크로 접근.
- **프론트엔드 라우트**: 모든 `/c/[token]/**` 경로 공통.
- **호출되는 API**: 미들웨어의 `verifyPinCookieEdge`(존재하지 않거나 만료·변조된 쿠키는 무효 처리) → 각 API 라우트의 `checkPinAuth`.
- **성공 시 기대 결과**: 해당 없음(정의상 실패 케이스).
- **실패 및 경계 상황**:
  - 존재하지 않는 토큰: `getProjectByToken`이 `null` 반환 → Figma `#56108` 기반 "이 링크는 사용할 수 없어요" 화면과 illustration을 표시한다. `작가에게 문의하기`는 invalid token으로 연락처를 조회할 수 없으므로 이전 페이지로 돌아가고 history가 없으면 서비스 루트로 이동한다. 각 데이터 API는 404/401을 반환한다.
  - 만료(25시간 경과 등)·변조 쿠키: 미들웨어가 무효로 판단해 `/pin?from=...`으로 리다이렉트(자동 테스트 `pin-auth.spec.ts` T3/T4로 회귀 검증됨).
  - `pin_verified_{token}` 쿠키가 있지만 다른 토큰용으로 서명된 경우(토큰 불일치)도 401/리다이렉트 처리됨(T3).
  - 쿠키 발급 후 프로젝트 PIN이 설정·변경·삭제된 경우 PIN 상태 불일치로 기존 쿠키를 무효 처리하고, PIN이 있으면 입력 화면으로 이동하며 고객 API 직접 호출도 401을 반환한다(M4).
- **관련 권한/인증 조건**: 없음(실패를 다루는 흐름이므로).
- **QA에서 확인해야 할 항목**: 만료 쿠키로 데이터 API를 직접 호출했을 때 401이 정확히 반환되는지, UI가 이를 "링크가 깨졌다"가 아니라 "다시 인증 필요"로 명확히 안내하는지(현재 만료 시 PIN 재입력 화면으로 자연스럽게 이동하므로 문제 없어 보이나, 문구 자체가 "인증 만료"를 명시하지는 않음 — 확인 필요).

## 11. 보정본 확인 및 재보정 요청

- **시작 조건**: `status`가 `reviewing_v1` 또는 `reviewing_v2`(작가가 보정본을 전달 완료).
- **사용자가 수행하는 단계**:
  - 고객이 `/c/[token]` 초대 링크로 진입하면 셀렉 인트로와 같은 `CustomerInviteIntro` 기반 라이트 화면에서 대표 사진, 담당 작가, 프로젝트명, 검토 기한, 남은 재보정 횟수를 확인하고 "보정본 검토하기"로 이동한다. `selecting`, `reviewing_v1`, `reviewing_v2`가 사진·작가 정보·반응형 구조·CTA 영역을 공유한다. PC·모바일 모두 `100dvh` 안에서 사진과 정보 패널을 배분해 좌우·상하 페이지 스크롤 없이 한 화면을 구성하며, 700px 이하의 짧은 모바일 화면에서는 hero·간격·정보 행을 함께 축소한다. 사진은 브라우저에서 사전 로드에 성공한 뒤에만 노출하고, URL을 기다리거나 로드에 실패하면 깨진 이미지 대신 라이트 브랜드 플레이스홀더를 유지한다.
  - (재보정 0회 프로젝트, `max_revision_count === 0`) 전체 보정본을 한 번에 확인 후 "수령 완료" 클릭.
  - (재보정 가능 프로젝트) 모바일·PC 모두 `/review` 목록에서 시작한다. 썸네일을 누르면 사진별 상세(`/review/[photoId]`)에서 원본/보정본 비교 후 `Y`(승인)/`R`(재보정 요청, 코멘트 최대 100자) 단축키로 처리한다. 상세의 사진 위에는 상시 회차·판단 배지를 겹치지 않고 파일명/회차는 앱바, 현재 판단은 우측 패널에 표시한다. PC는 사진 하단의 비교 버튼을, 모바일은 사진을 300ms 누르는 동안만 원본을 보여준다. 확대된 사진에서도 같은 길게 누르기로 원본을 확인한다. 하단 필름스트립과 검토 진행 영역은 같은 높이를 공유하며 `진행 → 사유 확인 → 작가에게 전달`로 내용만 바뀌어 레이아웃이 움직이지 않는다. `Esc`는 집중 보기부터 닫은 뒤 상세 화면에서 다시 누를 때 목록으로 돌아온다.
- **프론트엔드 라우트**: `/c/[token]/review` (분기: `DeliveryReceiptView`/`ReviewGalleryView`), `/c/[token]/review/[photoId]`.
- **호출되는 API**: `GET /api/c/review`(보정본+기존 리뷰 로드) → 사진별 승인/재보정 상태를 모아 `POST /api/c/review/submit` `{ token, reviews: [{photo_version_id, photo_id, status, customer_comment?}] }`로 일괄 제출. 서버는 현재 검토 대상 전체 제출, `photo_version_id`와 `photo_id`의 정확한 짝, 중복 여부, 코멘트 100자 제한을 다시 검증한다. 레거시 경로 `POST /api/c/review-submit`은 DB 프로젝트에 대해 `410 Gone`으로 차단하고 목업 데이터에만 남겨둔다.
- **사진 전환 성능**: 리뷰 응답에 이미 포함된 원본 프리뷰·보정본 URL을 재사용해 현재 보기 모드에 필요한 인접 사진을 `useAdjacentImagePreload`로 미리 다운로드·decode한다. PC 비교 화면은 양옆 1장의 원본/보정본 쌍, 모바일 단일 화면은 양옆 1장의 활성 탭 이미지만 대상으로 하며 데이터 절약 모드에서는 현재 사진만 로드한다. 비활성 썸네일은 lazy/low priority로 내려 메인 이미지와의 네트워크 경합을 줄인다. 별도 API 호출은 없다.
- **성공 시 기대 결과**: 서버가 `version_reviews`를 upsert하고, 재보정 요청이 하나라도 있고 `max_revision_count > 0`이며 아직 라운드 한도 내이면 `projects.status = "editing_v2"`(+`revision_round` 증가)와 함께 현재 최종 ZIP 후보를 `obsolete`로 만든다. 그렇지 않으면(전부 승인, 또는 재보정 한도 소진) `projects.status = "delivered"`와 `delivered_at`을 같은 상태 업데이트에서 기록하고 현재 후보를 최종 납품 대상으로 유지한다. DB 트리거와 CHECK 제약도 `delivered_at` 누락을 차단한다. `delivered` 화면에서는 `GET /api/c/final-delivery`와 `/archive`를 통해 원본 크기 최종 보정본 ZIP을 내려받는다.
- **확정 사진 보호**: 고객이 승인해 `version_reviews.status='approved'`가 된 보정본은 작가 화면에서 체크박스가 비활성화되고 전체 선택, 일괄 삭제, 개별·일괄 교체 대상에서 제외된다. 삭제 API와 FastAPI 보정본 업로드 API도 확정 상태를 다시 조회해 직접 호출을 409로 거부한다.
- **실패 및 경계 상황**:
  - 제출한 `photo_version_id`가 해당 프로젝트 소속이 아니면 400 반환("일부 보정본 ID가 이 프로젝트와 일치하지 않습니다").
  - `reviews` 배열이 비어있으면 400.
  - 재보정 요청이 있어도 이미 재보정 한도(`max_revision_count`)를 소진한 상태(`revision_round >= max_revision_count`)면 재보정 요청 여부와 무관하게 `delivered`로 전환됨 — 고객 입장에서는 "재보정을 요청했는데 왜 완료 처리됐는지" 혼란 가능성.
- **관련 권한/인증 조건**: PIN 쿠키, `checkPinAuth`. 서버가 `reviewing_v1`/`reviewing_v2` 상태를 제출 전과 조건부 상태 업데이트 시점에 확인하므로 완료 후 재제출과 빠른 중복 상태 전환을 거부한다.
- **QA에서 확인해야 할 항목**: 재보정 요청 코멘트 100자 제한 UI/서버 양쪽 일치 여부, 재보정 한도 마지막 라운드에서 재보정 버튼이 실제로 비활성화되는지, `reviewing_v1`이 아닌 상태(예: `selecting`)에서 이 API를 직접 호출했을 때 서버가 거부하는지.

## 3. 프로젝트 상세 허브 및 고객 프로젝트 설정

- **시작 조건**: 프로젝트 생성 완료, `/photographer/projects/[id]` 진입.
- **사용자가 수행하는 단계**: 상단 Breadcrumb(`프로젝트 > #프로젝트ID`)으로 프로젝트 목록에 돌아가거나, 공통 Light Page Header에서 프로젝트 ID·프로젝트명·촬영 정보를 확인하고, 바로 아래 6단계 Expanded Stepper에서 현재 진행 위치를 확인한다. Desktop 본문 왼쪽의 통합 프로젝트 설정에서 고객명·촬영일·장소·검토 기한·필요 장수(N)·촬영 종류·고객 연락처·재보정 횟수·납품 파일·고객 링크/PIN을 확인하고 오른쪽 현재 작업 패널에서 상태에 맞는 작업으로 이동한다. Mobile은 현재 작업 패널을 프로젝트 정보보다 먼저 배치하고 장문 설명·actor badge·행형 meta를 한 줄 요약으로 축약한다. 프로젝트 정보는 접기 기능 없이 상세 정보를 항상 표시한다. Mobile detail intro는 전역 A-CUT 로고와 중복되는 뒤로가기 icon을 제거하고 카드와 같은 20px 왼쪽 기준선에서 26px 프로젝트명(최대 2줄)과 `촬영유형 · YYYY.MM.DD 촬영`만 표시한다. 6단계 progress card는 active node 자체로 현재 위치를 전달하므로 `현재 · 단계 · 상태` summary를 반복하지 않고 80px 이하의 단일 stepper 행으로 축소한다. 상세 화면을 스크롤하면 공통 모바일 헤더가 44px로 축소되고 `A-CUT.` 워드마크와 프로필 대신 `A 심볼 + 프로젝트명 · 고객명 고객`을 한 줄로 표시한다. 프로젝트명은 남은 폭에서 말줄임하고 고객명은 최대 42% 폭을 확보해 두 정보가 함께 보이게 한다. 최상단으로 돌아오면 전체 브랜드 헤더를 복원하며, 이 프로젝트 context 전달 규칙은 원본·셀렉·보정본·최종본 자산 화면과 같은 공통 컴포넌트를 사용한다. Desktop과 Mobile 모두 Page Header에는 overflow action을 두지 않고 Information Card header의 `···` 메뉴에서 `수정하기/삭제하기`를 실행한다. 프로젝트 목록 카드에서도 `···` 관리 메뉴를 제거하고 카드와 다음 작업 CTA는 진입만 담당하며, 수정·삭제는 상세 Information Card에서만 실행한다. 값이 없는 선택 항목은 숨기고, 업로드 전 고객 링크 영역은 disabled control 대신 생성 조건 안내 한 줄만 표시한다. `수정하기`를 누르면 프로젝트 생성과 동일한 840px 폼 구조로 전환되어 같은 Section·Field·Input·Selector·Switch·PIN control로 프로젝트명·촬영 유형·고객·촬영일·연락처·촬영장소와 갤러리 설정을 편집한다. Mobile 수정 view는 `프로젝트 정보 수정` 타이틀과 뒤로가기를 시각적으로 제거하고 접근성 제목만 유지해 전역 브랜드 헤더 다음에 `기본 정보` section이 바로 시작되며, 이탈은 하단 `취소`로 통일한다. Desktop 수정 view는 기존 Page Heading과 뒤로가기를 유지한다. 고객 PIN은 이 수정 view에서 4자리 숫자로 설정·변경하거나 사용 스위치를 꺼 제거할 수 있고, 셀렉 기한은 우선 노출하지 않는다. 생성 폼과 수정 view의 하단 저장 영역은 공용 `PhotographerFormActionBar`가 surface·divider·sticky 동작을 관리하며 각 화면이 안내와 액션을 주입한다. 작업 패널은 `preparing + photo_count=0`이면 원본 업로드 시작, `preparing + photo_count>0`이면 업로드 현황, `selecting`이면 셀렉 현황, 보정 상태면 워크플로우, 검토 상태면 보정본 현황, `delivered`이면 프로젝트 결과로 안내한다. Project Detail에는 별도 최근 활동 패널을 표시하지 않는다.
- **프론트엔드 라우트**: `/photographer/projects/[id]` (`ProjectNexusPageClient.tsx`, 상세/전체 편집 view 전환).
- **호출되는 API**: 상세 데이터 조회 외에, 정보 수정 시 `PATCH /api/photographer/projects/{id}` — 세션+소유권 확인 후 `location`, `access_pin`을 포함한 필드를 갱신한다. PIN은 빈 값 또는 정확한 4자리 숫자만 허용하고 납품 완료 전까지 변경할 수 있다. "현재 작업" 패널은 상태를 변경하지 않고 기존 업로드·워크플로우·결과 화면으로 이동만 한다.
- **성공 시 기대 결과**: 화면에 즉시 반영("프로젝트 정보가 저장되었습니다" 토스트).
- **실패 및 경계 상황**: 프로젝트명·고객명·촬영일·셀렉 장수·연락처·PIN 검증 오류는 생성 화면과 같이 해당 field 아래에 표시한다. 필요 장수(N)는 `["preparing", "selecting"].includes(status)`일 때만 수정 가능(`canEditN`)이고, 원본 설정은 원본 업로드 시작 후 잠긴다. PIN은 `delivered`에서만 잠긴다. 서버는 잠긴 설정의 동일값 재전송은 허용하되 실제 변경은 거부한다. 서버 저장 실패나 업로드 사진 수보다 큰 셀렉 수처럼 field 하나로 환원하기 어려운 오류는 폼 하단에 표시한다.
- **관련 권한/인증 조건**: 로그인 세션 + `project.photographer_id` 일치.
- **QA에서 확인해야 할 항목**: `confirmed` 이후 상태에서 N을 수정하려는 시도가 실제로 UI/서버 양쪽에서 막히는지, 촬영장소와 PIN 저장 후 상세 정보에 즉시 반영되는지, PIN 제거 시 고객 접근 흐름이 PIN 없는 프로젝트로 동작하는지.

## 4. 사진 업로드

- **시작 조건**: `status === "preparing"`. 초대 링크 활성화 뒤 원본은 더 이상 이 편집 화면에서 관리하지 않고 §6의 읽기 전용 원본 탭에서 확인한다.
- **사용자가 수행하는 단계**: 파일 선택(드래그앤드롭 또는 파일 다이얼로그) → 업로드 확인 모달에서 프로젝트의 원본 포함 설정을 확인(PC는 선택 파일 총 용량도 표시) → 자동 압축 → 업로드 진행률 확인 → 사진 상세 뷰어에서 고객 진입 대표 사진 지정 → 프로젝트 목록·대시보드 카드에서도 해당 대표사진 확인 → (N장 이상 업로드 완료 시) `셀렉 요청하기` 클릭 → 요청 모달에서 고객·셀렉 장수·원본 다운로드 설정과 셀렉 마감일을 확인 → 추천이 있으면 최대 5장의 썸네일을 확인하고 `확인·수정`으로 추천 필터에 복귀(추천이 없으면 `추천 사진 추가`) → 원본 사진의 추가·삭제·교체가 제한됨을 확인하는 checkbox 선택 → 활성화된 `셀렉 요청하기`로 요청 시작 → 성공 후 공유 모달에서 링크/PIN 복사. 대표사진이 없거나 삭제된 경우 목록과 고객 진입 화면은 첫 사진으로 폴백한다. 모바일 요청 모달은 고객명과 `셀렉 N장 · 원본 M장 · 다운로드 여부`, 추천 요약, 마감일, 한 문장 잠금 동의를 보여주며 링크/PIN은 성공 후 공유 모달에서만 제공한다. 빠른 마감일은 `+3/+7/+15일`, 하단은 단일 요청 CTA로 축약하고 가로 스크롤을 허용하지 않는다. 알림톡은 준비 중인 비활성 버튼이며 이벤트가 없다. HEIC 파일이 포함된 원본 포함 프로젝트는 HEIC 건수 경고를 표시하고 해당 파일은 썸네일만 업로드한다. 드래그앤드롭은 데스크톱에서만 활성화(모바일 비활성화).
- **모바일 표시·삭제 규칙**: 업로드된 사진은 3열·1:1 썸네일·6px 간격으로 표시하며 고객 셀렉 카드와 동일한 무테 `PhotoThumbnailFrame`을 사용한다. 사진을 450ms 길게 누르면 짧은 진동과 함께 해당 사진이 선택된 관리 모드로 진입하고, 선택 사진의 frame에 2px 주황색 inset과 모든 사진 좌측 상단 22px 갤러리 공통 사각 checkbox가 나타난다. 이후 사진 탭은 상세보기 대신 다중 선택을 토글하고 매 변경마다 지원 기기에서 10ms 진동을 제공한다. 상단은 `사진 선택`과 별도 장수 pill로 안정적으로 유지하며 취소는 상단에만 둔다. 하단에는 `선택한 사진 N장 삭제` 단일 CTA를 표시하고, 0장이면 `삭제할 사진을 선택하세요`로 비활성화한다. 삭제 확인 dialog는 모바일에서 어색한 고아 글자 줄바꿈이 생기지 않도록 `원본 N장을 삭제할까요?`로 선택 장수를 명시하고 복구 불가 안내 뒤 danger CTA `원본 삭제`로 실행한다. 손가락이 10px 이상 움직이면 long press를 취소해 스크롤을 우선하며, 최초 한 번은 long press 안내 toast를 표시한다. 일반 toolbar에는 `전체삭제`를 직접 노출해 모든 원본 삭제 흐름을 유지한다. 취소하거나 선택 삭제가 끝나면 선택을 비우고 일반 상세보기 모드로 복귀한다. 하단 action bar는 gallery와 별도 flex 영역을 차지하고 gallery 자체에도 하단 여백을 유지해 마지막 사진을 가리지 않는다. 갤러리의 독립 스크롤을 내리면 원본 자산 화면과 동일한 임계값으로 페이지 헤더와 공통 brand header를 단계적으로 축소하고, 위로 이동하거나 최상단으로 돌아오면 복원한다. 목록보기와 데스크톱 사진 비율은 변경하지 않는다.
- **프론트엔드 라우트**: `/photographer/projects/[id]/upload`. `preparing`이 아닌 프로젝트가 이 URL로 직접 진입하면 `/photographer/projects/[id]/assets/original`로 replace 이동한다. 셀렉 요청 직후에는 공유 모달을 먼저 보여주기 위해 현재 업로드 화면을 유지하고, 이후 재진입부터 원본 탭으로 연결한다.
- **호출되는 API**:
  1. 클라이언트 압축(`compressImagesInParallel`, 워커 풀 기반 — 이 화면 전용, `include_original` 값과 무관하게 **항상** 실행됨. 서버 호출 아님). `include_original=true`일 때도 압축본이 `/api/upload/photos`로 전송되며, **별도로** 압축되지 않은 브라우저 원본(`rawFile`)이 R2로 직접 PUT된다 — 즉 이 경우 같은 사진이 압축본(BE 경유)과 원본(R2 직접)으로 두 번 전송된다. 상세 배치/동시성/barrier 구조는 `docs/upload-flow.md` 참고.
  2. `POST {NEXT_PUBLIC_API_URL}/api/upload/photos`(FastAPI, Bearer JWT) — 실패 시 `POST /api/photographer/upload/photos`(Next 프록시)로 폴백. 파일 선택 시 생성한 `client_upload_id`를 두 경로와 모든 XHR 재시도에서 그대로 재사용하며, 서버의 `(project_id, client_upload_id)` UNIQUE/RPC가 응답 유실 뒤 중복 사진·원본 job 생성을 차단한다.
  3. `include_original=true`일 때 응답의 `original_presigned`를 파싱 → R2에 presigned PUT(브라우저→R2 직접, BE 비경유) → `POST /api/photographer/upload/originals/confirm`(`job_id`) 순서로 처리(각 파일별 순차, 오류는 non-fatal로 경고만). 이 확인(confirm) 응답까지 받아야 해당 배치가 완료 처리된다 — "업로드 완료" 토스트는 이 단계까지 포함해서 기다린다.
  4. N장 이상 업로드 완료 후 요청 모달에서 선택한 `deadline`을 프로젝트 PATCH로 저장하고, 사진 구성 잠금 안내를 확인한 작가가 `셀렉 요청하기`를 누르면 `PATCH /api/photographer/projects/{id}/status` `{status:"selecting"}`를 수동 호출한다. 성공 후 요청 모달을 닫고 로컬 프로젝트 상태와 기한을 갱신한 뒤 링크 공유 모달을 연다.

## 5. 고객 링크 및 PIN 확인

- **시작 조건**: 프로젝트가 이미 존재(생성 시 PIN을 넣지 않았어도 무방).
- **사용자가 수행하는 단계**: 프로젝트 상세 조회 view에서 고객 PIN을 읽기 전용으로 확인하거나 표시/숨김을 전환하고, `초대 링크 복사`로 링크와 설정된 PIN을 함께 클립보드에 복사한다. PIN 설정·변경·삭제는 같은 페이지의 `정보 수정` 전체 view에서 수행한다. `알림톡 보내기`는 향후 구현 예정인 비활성 버튼으로 표시되며 클릭 이벤트가 없다.

- **성공 시 기대 결과**: 초대 링크와 PIN이 복사되고 토스트가 표시된다. 이후 고객이 이 링크에 접근하면 §Part1-2 또는 §Part1-3 흐름을 따른다. PIN 설정·변경·삭제 시 기존 고객 인증 쿠키는 즉시 무효가 되어 다음 페이지 요청과 고객 API 요청부터 새 PIN 상태를 적용한다.

- **관련 권한/인증 조건**: 로그인 세션 + 소유권.
- **QA에서 확인해야 할 항목**: PIN이 있는 프로젝트와 없는 프로젝트에서 복사 문자열이 각각 올바른지, 수정 view에서 4자리 PIN 변경·랜덤 생성·제거가 저장되는지, 준비 중 프로젝트에서 복사 버튼이 비활성인지, 알림톡 버튼이 이벤트 없이 비활성 상태인지 확인한다.

Mobile asset header는 breadcrumb와 `원본 갤러리/셀렉 결과/보정본 업로드/최종본 갤러리` 같은 중복 화면명을 시각적으로 숨기며, 탭 위의 고객명·프로젝트 코드 context row도 표시하지 않는다. 모든 모바일 작가 페이지의 공통 브랜드 헤더는 하단 회색 divider 없이 동일하게 표시한다. 자산 화면 최상단에서는 전체 브랜드 헤더 다음에 44px 터치 영역과 36px face의 자산 탭이 바로 시작된다. 스크롤 축소 상태에서는 공통 48px 헤더의 `A 심볼` 옆에 프로젝트명만 표시한다. 원본 탭의 읽기 전용·공유 상태 안내는 화면 맥락과 중복되므로 별도 pill이나 bar로 표시하지 않는다. Mobile toolbar는 탭별 대표 작업과 우측 끝의 공통 `사진 작업 더보기`를 한 줄에 표시한다. 분석 결과가 있는 원본의 유사컷 trigger는 고객 갤러리와 동일한 `유사컷 + 그룹 수` 공통 CTA를 사용하며, 활성 여부는 ON/OFF 문구 대신 버튼의 색과 `aria-pressed`로 전달한다. 필터/정렬과 갤러리/목록 전환은 더보기 bottom sheet에서 제공하며 적용된 도구 수는 더보기의 Orange badge로 확인한다. 갤러리를 아래로 스크롤하면 toolbar는 사라지고 compact global header와 file tab만 남아 사진 영역을 확보한다. Mobile 하단 고객 상태 CTA는 viewport와 safe area에 고정되며 동일 높이의 본문 spacer가 마지막 사진을 보호한다. 납품 완료 상태에서는 더 실행할 작업이 없으므로 모바일 하단 상태 바와 spacer를 모두 표시하지 않는다. Desktop은 높이 40px의 `프로젝트 > 프로젝트명` breadcrumb 우측에 `고객명 고객 · #프로젝트ID`를 배치한 뒤 file tab·노출형 검색·정렬·보기 controls·sticky 하단 action으로 이어진다. 셀렉 결과의 상태 전환 CTA는 공용 하단 `PhotographerPageActionBar`에 고정하며, 납품 완료 후에는 탭과 관계없이 이동 CTA 대신 읽기 전용 `납품 완료` 상태를 표시한다. 확정 이후에는 셀렉 결과를 CSV/TXT로 내보내거나 파일명을 복사하고, 원본 포함 여부에 따라 셀렉 원본 또는 프리뷰를 다운로드한다.
- **유사컷 대표컷 변경**: `selecting` 상태의 작가 원본 상세보기에서 그룹 필름스트립으로 사진을 이동한 뒤 `대표컷 지정`을 누르면 고객 갤러리에 먼저 보일 대표 사진을 변경한다. 현재 대표컷은 체크 상태로 표시하고 재지정을 막으며, 저장 중에는 중복 요청을 차단한다.
- **Mobile 셀렉 도구**: toolbar에서 중복되는 `셀렉 사진 N장` summary를 제거한다. 셀렉 결과 내보내기를 대표 작업으로 직접 표시하고, 공통 `사진 작업 더보기`에서 검색/정렬과 갤러리/목록 전환을 제공한다. 자산 탭은 44px 터치 영역 안에 36px face를 사용하고 toolbar·gallery와 12px 좌우 정렬선을 공유한다. 셀렉 grid는 toolbar와 10px만 띄운 기본 2열·6px 간격으로 표시하며 filename은 12px Medium 한 줄을 유지한다. 고객 코멘트는 반복 라벨 없이 한 줄로 줄여 사진 탐색 밀도를 유지한다.
- **셀렉 grid 정렬 안정성**: 가상화 행 높이는 현재 사진 순서와 사진별 코멘트 유무를 함께 키로 사용한다. 파일명·코멘트 우선 정렬로 코멘트 카드가 다른 행으로 이동하면 높이를 즉시 다시 측정해 큰 공백이나 카드 잘림이 남지 않게 한다.
- **Mobile 보정본·최종본 도구**: 두 탭도 같은 compact 공통 toolbar와 surface 규칙을 사용한다. 보정본 상단에서는 중복되는 `1차 보정 · N장` 요약과 `일괄 업로드/교체`를 제거하고 상태 필터와 갤러리/목록 전환만 44px 공통 아이콘 버튼으로 표시한다. 활성 필터 수는 필터 아이콘의 Orange badge로 확인한다. 보정본 Mobile 내보내기는 제거하고 PC 내보내기는 유지한다. grid는 기본 2열·8px 간격이며 작업이 남아 있는 동안 고객 상태/다음 단계 action bar를 viewport 하단과 safe area에 고정한다. 현재 보정 단계의 업로드가 일부라도 남아 있으면 하단 action bar는 진행 수와 Primary `일괄 업로드`를 표시하고, 모든 대상 업로드가 완료된 뒤 `보정본 검토 요청`으로 전환한다. 납품 완료 후에는 모바일 action bar를 제거한다. Desktop toolbar와 검토 요청 CTA는 그대로 유지하고 납품 완료 상태만 읽기 전용으로 표시한다. 보정본 카드 파일명은 다른 자산 탭과 같은 12px Medium·Muted 위계를 사용한다.
- **최종본 초기 상태**: `/assets/final`은 첫 화면부터 내부 회차를 `final`로 초기화한다. 납품 완료 전 재보정 요청이 있었더라도 V1/V2 작업 상태를 먼저 그리지 않으며, 사진별 마지막 확정 버전과 `최종 확정본` 요약만 표시한다.
- **모바일 최종본 내보내기**: 선택지가 세 개인 내보내기는 전체 화면 dim과 하단 시트를 사용하지 않는다. toolbar 다운로드 아이콘 아래에 compact popover를 열어 파일명 CSV, 코멘트 포함 CSV, 셀렉 원본 다운로드를 제공한다. 바깥 영역과 Escape로 닫을 수 있으며 투명 click-away layer는 배경 사진을 어둡게 가리지 않는다.
- **최종본 표시 범위**: PC와 Mobile 모두 최종본 탭의 사진 항목에는 최종 보정본 파일명과 이미지만 표시한다. 원본 참조, 확정 상태 badge, 고객 코멘트와 버전 이력/비교 UI는 보정본 탭에 남기고 최종본 grid·list·viewer에서는 숨긴다.
- **프론트엔드 라우트**: `/photographer/projects/[id]/assets/original|selected` (`assets/ProjectAssetsPageClient.tsx`). 원본과 셀렉은 각각 독립된 경로라 새로고침·직접 링크가 가능하며 공용 `ProjectAssetTabs`로 이동한다. 업로드 화면과 자산 화면은 공용 `PhotographerPhotoGallery`의 가상화 grid/list, 이미지 로딩 queue, filename formatting을 공유한다. 자산 화면에서는 선택·삭제·업로드 기능을 주입하지 않는다. 원본 grid는 PC와 Mobile 모두 이미지 상단에 한 줄 파일명을 표시하며 Mobile 2열에서는 ellipsis로 카드 높이를 고정한다. 셀렉 grid도 원본과 같이 파일명만 사진 위에 표시하고 별도 순번을 붙이지 않으며, 셀렉 코멘트는 사진 아래에 내용이 있을 때만 한 줄로 표시한다. 셀렉 list 역시 별도 번호 열 없이 사진·파일명·셀렉 코멘트만 제공한다. Desktop의 원본·셀렉·보정본 grid는 동일한 최소 카드 폭(218px), 12px 간격, 반응형 좌우 여백과 사진 비율을 사용한다. Mobile 원본·셀렉 탭은 비교 탐색을 위해 최소 2열·8px 간격으로 시작하며 보정 variant와 업로드 화면에는 이 강제 열 수를 적용하지 않는다. 양쪽 상세보기는 공용 viewer shell의 필름스트립·키보드 이동을 사용한다. 셀렉 상세보기는 해당 사진의 셀렉 코멘트가 있을 때만 desktop 우측 inspector 또는 mobile stage 하단 compact panel을 표시하며, 사진이 바뀌면 긴 코멘트의 스크롤을 처음으로 되돌린다. 모바일 셀렉 상세는 보정 상세와 같은 좌우 8px stage, 핀치 확대, compact filmstrip을 사용한다. 파일명과 현재 순번은 header에서만 제공해 중복 노출하지 않는다.
- **호출되는 API**: 워크플로우 기본 데이터는 `src/lib/db.ts` 조회와 `GET /api/photographer/projects/{id}/versions`를 사용한다. 셀렉 원본 다운로드는 `POST /api/photographer/projects/{id}/selected-originals`가 세션·소유권·`include_original`·확정 상태를 검증하고 `selections.is_selected=true`를 서버에서 다시 조회한 뒤 FastAPI presign을 호출한다(클라이언트가 photo id를 지정하지 않음).
- **성공 시 기대 결과**: `getPhotosWithSelections()` 한 번으로 받은 전체 사진·선택 ID를 탭별로 파생해 중복 네트워크 조회 없이 전환한다. CSV(`파일명,코멘트`)와 TXT(파일명 목록) 다운로드, 클립보드 복사 시 토스트 표시. 셀렉 원본/프리뷰는 PC Chrome/Edge의 폴더 선택기를 먼저 열고 presigned 파일을 한 장씩 해당 폴더로 스트리밍하며 진행 장수와 완료 알림을 표시한다. 프리뷰는 실제 포맷에 맞게 원래 파일명의 stem 뒤에 `_preview.jpg`를 붙인다. 같은 파일명이 이미 있으면 덮어쓰지 않고 `(2)`, `(3)` 접미사를 붙인다.
- **라이트박스 성능**: 결과 라이트박스가 열려 있을 때 `viewerImageUrl(photo)` 기준으로 PC는 이전 1장·다음 2장, 모바일은 양옆 1장의 1200px 프리뷰를 미리 다운로드·decode한다. 기존 그리드 썸네일 선로딩과 분리되어 있으며 원본 크기 파일은 대상이 아니다.
- **실패 및 경계 상황**: 셀렉 파일 다운로드는 고객 확정 전(`preparing`/`selecting`)에 비활성화된다. 원본 포함 프로젝트에서 선택된 원본 중 `original_status !== completed`이거나 R2 원본 키가 없는 사진이 하나라도 있으면 프리뷰로 자동 대체하거나 일부만 저장하지 않고 누락 장수를 포함한 409로 중단한다. 원본 미포함 프로젝트는 최대 1200px JPEG가 보정·납품용으로 부족할 수 있음을 메뉴에 명시한다. File System Access API가 없는 브라우저에서는 불안정한 자동 다중 다운로드로 폴백하지 않고 PC용 Chrome/Edge 사용을 안내한다.
- **관련 권한/인증 조건**: 로그인 세션 + 소유권.
- **QA에서 확인해야 할 항목**: 코멘트에 쉼표/줄바꿈이 포함된 경우 CSV 이스케이프(`csvEscape` 함수 존재 확인됨)가 실제로 스프레드시트에서 깨지지 않는지, 특수문자 포함 파일명의 TXT 내보내기, 셀렉 원본의 서버 조회 수와 폴더 저장 수 일치, 사용자 폴더 선택 취소 시 오류 미표시, 중간 네트워크 실패 시 완료로 잘못 표시하지 않는지.

## 7. 보정본 업로드 및 전달

- **시작 조건**: `status === "confirmed"`(V1) 또는 `status === "editing_v2"`(V2, 고객이 재보정을 요청한 경우에만 존재).
- **사용자가 수행하는 단계**:
  1. "보정 시작" 클릭 → `confirmed → editing` 전환.
  2. 보정된 파일을 원본과 매칭해 업로드. 매칭은 4단계 순서로 자동 시도된다: ① 파일명 완전 일치 → ② 편집 툴 접미사 제거 후 유사 파일명 → ③ CLIP 이미지 유사도 → ④(2026-07-13 추가) 위 세 단계 모두 실패한 잔여 사진·잔여 파일을 순서대로 짝짓는 최후 폴백("순서" 배지로 표시, 근거가 약하므로 작가가 확인 후 "변경"으로 재지정 가능).
  3. "고객에게 전달" 클릭 → `editing → reviewing_v1` 또는 `editing_v2 → reviewing_v2` 전환.
- **프론트엔드 라우트**: `/photographer/projects/[id]/assets/retouched`(**실제 사용되는 유일한 V1/V2 업로드·전달 화면** — 프로젝트 상세 허브의 모든 보정 관련 버튼이 여기로 연결되며 `UploadVersionsPanel.tsx`가 업로드를 담당). 기존 `/workflow`와 `/results?tab=original|selected`는 저장된 링크 호환을 위해 새 `/assets/*` 경로로 redirect한다.
- **보정 회차 탐색**: 보정본 화면 안에서 `1차 보정`과 `재보정`을 전환한다. Desktop은 별도 라운드 행을 두지 않고 작업 도구줄의 Neutral Segment로 회차를 선택하며, 이어지는 `업로드 N/M장` 진행 막대와 `N장 남음`, 상태 필터를 한 흐름으로 읽는다. Mobile은 상위 자산 탭과 경쟁하지 않도록 compact select를 사용하고 `N/M장 업로드`를 같은 44px 도구줄에 표시한다. `재보정`은 허용 횟수만으로 미리 노출하지 않고 V1 `revision_requested`, V2 파일, 또는 `editing_v2`/`reviewing_v2` 상태가 실제로 존재할 때만 생성한다. 상태가 바뀌어도 열어 둔 V1 검토 결과를 V2가 강제로 덮지 않으며, `?round=v1|v2`로 새로고침 후 선택 라운드를 복원한다. V1 탭은 확정·재보정 요청 결과와 고객 코멘트를 보존해 보여주고, 결과 필터는 `전체`·`확정`·`재보정 요청`만 제공한다. V2 탭은 재보정 요청 사진만 작업 대상으로 표시한다. Mobile 목록은 각 사진을 `원본 thumbnail+실제 filename → 보정본 thumbnail+실제 filename` 68px 한 줄로 표시하고 파일명은 ellipsis 처리한다. `원본명 유지` 대체 문구는 사용하지 않는다. 하단 작업 막대는 현재 열어 본 라운드가 아니라 프로젝트의 실제 다음 단계에 맞춰, 미완료 상태에서는 남은 V1/V2 업로드 또는 교체 CTA를 표시하고 업로드·매칭이 완료된 뒤에만 해당 검토 요청 CTA로 바뀐다. V1/V2 안에서 파일을 다시 교체해도 별도 V3나 추가 검토 회차를 만들지 않으며, 교체 전 파일과 당시 검토 결과만 별도 스냅샷 이력으로 보존한다.
- **보정본 검토 요청**: 업로드·매칭이 완료되면 요청 모달에서 고객명, 검토 회차, 대상 사진 수와 선택 가능한 검토 기한을 확인한다. 요청 전 설정 화면은 링크/PIN을 반복 노출하지 않으며, 상태 전환이 성공한 뒤 별도 공유 모달에서 고객 링크와 비밀번호를 복사한다. 모바일은 빠른 기한을 `+3/+7/+15일`과 단일 요청 CTA로 축약한다.
- **호출되는 API**:
  - `PATCH /api/photographer/projects/{id}` 또는 `.../status` `{status:"editing"}` (보정 시작).
  - `POST {API_URL}/api/upload/versions/delivery/presign` → 보정 원본을 R2에 direct PUT → `POST {API_URL}/api/upload/versions`(FastAPI 직접, Bearer JWT) — delivery HEAD 검증, 고유 key에 검토용 1200px/82% + 300px/75% 생성, `replace_photo_versions_with_history` RPC가 기존 활성 파일·검토 결과를 이력에 보존한 뒤 현재 `photo_versions`를 교체한다.
  - 매칭 보조: `POST /api/photographer/projects/{id}/retouch-match`(clip-service 프록시, 파일명 매칭 실패 시 유사도 기반 추천).
  - 전달: `PATCH .../status` `{status:"reviewing_v1"|"reviewing_v2"}`가 `start_retouch_review_with_archive` RPC를 호출해 최종 납품 후보 스냅샷 생성과 상태 전환을 한 트랜잭션으로 처리한다.
- **성공 시 기대 결과**: 고객 검토가 즉시 활성화되고 백그라운드에서 원본 크기 보정본 ZIP 후보가 생성된다. V2 회차는 사진별 최신 V2가 있으면 V2, 없으면 V1을 포함하므로 부분 재보정도 지원한다. 워크플로우 비교 뷰어는 현재 탭의 앞뒤 사진만 미리 다운로드·decode하고, 분할 비교에서는 다음 이동에 실제 필요한 두 버전만 대상으로 제한한다. 작가 상세 뷰어의 `버전 이력`에는 현재 V1/V2와 같은 단계에서 교체된 과거 파일이 함께 표시되지만, 과거 항목은 읽기 전용이며 고객 공개 파일과 검토 상태를 바꾸지 않는다.
- **실패 및 경계 상황**: 선택 사진 중 원본 크기 보정본이 하나라도 없으면 고객 검토 시작을 409로 차단한다. 파일당 100MiB를 초과하면 presign 전에 차단한다. 동일 단계 파일 교체는 프로젝트 상태나 재보정 허용 횟수를 변경하지 않으며, 고객은 현재 활성 파일만 확인한다. 저장 RPC가 실패하면 새로 생성한 검토용·납품용 자산만 정리하고 기존 활성 파일과 과거 이력은 유지한다.
- **삭제 잠금**: 보정본 삭제는 해당 회차의 작가 작업 중 상태(`editing`, `editing_v2`)에서만 가능하다. 고객 검토가 시작되어 `reviewing_v1` 또는 `reviewing_v2`가 되면 전체 선택·개별 선택·선택 삭제와 업로드 패널의 기존 파일 삭제가 모두 사라지고 남아 있던 선택도 초기화된다. 직접 DELETE 요청도 서버가 409(`customer_review_in_progress`)로 거부해 고객이 검토 중인 파일을 보호한다.
- **기존 보정본**: 마이그레이션 전에 저장된 `photo_versions`의 1200px 검토 이미지를 원본 크기 파일로 가장해 백필하지 않는다. 아직 `editing`/`editing_v2`인 프로젝트는 해당 보정본을 원본 파일로 다시 업로드해야 다음 검토를 시작할 수 있으며, 이미 `reviewing_*`/`delivered`인 프로젝트에는 최종 ZIP이 소급 생성되지 않는다.
- **관련 권한/인증 조건**: 로그인 세션(Supabase JWT를 FastAPI에 직접 전달), 소유권.
- **QA에서 확인해야 할 항목**: `canUploadV1`/`canUploadV2` 조건(`editing`/`editing_v2`) 밖의 상태에서 업로드 시도 시 UI 차단 여부, 파일명 매칭이 실패했을 때 CLIP 매칭 제안 UI의 정확도, 순차 폴백("순서" 배지)으로 잘못 매칭된 경우 "변경"으로 정상 재지정되는지.

## 8. 납품용 원본 업로드 및 고객 다운로드

> **정정(2026-07-31)**: 이 섹션은 과거 `delivered` 상태 이후 별도로 원본을 업로드하던 `delivery_files`/`DeliveryUploadPanel` 방식을 기술하고 있었으나, 그 방식은 2026-07-23에 완전히 제거되었다(`DROP TABLE delivery_files`, 관련 컴포넌트/엔드포인트 삭제). 아래는 현재 코드 기준 실제 흐름이다.

### 8.1 원본 업로드 (작가)

- **시작 조건**: 프로젝트 생성 시 "원본 포함" 옵션(`include_original=true`)을 선택 — `preparing` 상태이고 아직 사진을 한 장도 올리지 않은 경우에만 이후에 옵션을 바꿀 수 있다.
- **사용자가 수행하는 단계**: `/photographer/projects/[id]/upload`에서 셀렉용 이미지와 원본을 함께 업로드(같은 파일 선택 동작 — 별도의 "납품 파일 업로드" 화면은 없음).
- **호출되는 API**: `POST /api/upload/photos`(FastAPI, `include_original=true`) — 썸네일/프리뷰는 즉시 R2 업로드, 원본은 브라우저가 presigned PUT으로 R2에 직접 올린 뒤 `POST /api/upload/originals/confirm`으로 확인. `original_jobs` 비동기 큐(`original_compress_worker`)는 재압축 없이 5초 폴링으로 R2 HEAD만 재확인한다. 브라우저가 PUT한 `originals/source/{project_id}/{hex}.{ext}` 키를 그대로 `photos.r2_original_url`로 확정하고, HEAD에서 확인한 실제 원본 크기를 `photos.original_compressed_size`에 저장한다. 컬럼명에는 `compressed`가 남아 있지만 현재 의미는 재압축 크기가 아닌 원본 객체 크기다. 과거 재압축 함수(`_process_original_sync`)는 코드에 남아 있지만 호출부가 없다.
- **실패 및 경계 상황**: 활성화 이후 새 사진 추가는 FastAPI와 DB 트리거가 409로 거부한다. 기존 `client_upload_id`의 응답 유실 replay와 이미 생성된 원본 job의 PUT/confirm/recover는 계속 허용한다.

### 8.2 납품용 원본 다운로드 ZIP 아카이브 (신규, 2026-07-31)

- **시작 조건**: `include_original=true` 프로젝트가 활성 상태이고 전체 사진의 `original_status='completed'`인 경우. 고객 링크 활성화 시 원본이 이미 완료됐다면 즉시, 아니면 마지막 `complete_original_job` 이벤트가 `enqueue_original_archive_build`를 호출한다.
- **흐름**: `activate_project_for_selection`은 프리뷰 사진 구성을 잠그고 고객 셀렉만 시작한다. 원본 완료 이벤트가 기존 멱등 archive enqueue RPC를 호출하고, 이후 백그라운드 워커가 기본 500MiB 단위로 `original_archive_parts`를 만든다. 전체 파트 완료 시 `original_archive_status='ready'`가 된다.
- **초대 링크 활성화**: 실제 사진 수가 셀렉 목표 이상이고 현재 브라우저의 프리뷰 업로드가 끝났으면 원본 `awaiting_upload/pending/processing/failed` 여부와 무관하게 활성화한다. 활성화 이후 새 사진은 추가할 수 없지만 기존 원본 job은 계속 전송·확인·복구한다.
- **다운로드 30일 기한**: 모든 archive part가 완료되어 ZIP이 실제 `ready`가 될 때 `original_download_started_at`을 최초 1회 기록하고 그 시점부터 30일을 계산한다. 링크를 먼저 열어도 원본 준비 시간만큼 다운로드 기간이 줄지 않는다.
- **활성화 후 변경 금지**: 프로젝트가 `preparing`을 벗어난 이후에는 원본이 포함된 사진의 추가/삭제가 API 레벨에서 거부된다. 따라서 ZIP은 초대 링크 활성화 시점의 확정된 스냅샷으로 생성된다.
- **stuck 복구**: `archive_sweep_worker`(`app/archive.py`, 서버 lifespan에서 `original_archive_worker`와 함께 기동, 30분 주기)가 `recover_stuck_original_archive_builds` RPC(part 생성 전 프로젝트 claim, 15분 초과 `processing` 복구)와 `recover_stuck_original_archive_parts` RPC(ZIP 빌드+업로드 중인 part, 45분 초과 `processing` 복구 — part 크기가 클수록 처리 시간이 길어질 수 있어 build claim보다 여유를 둠)를 호출해 archive 빌드가 영구히 멈추지 않게 한다 — `original_jobs`의 `stuck_job_sweep_worker`와 같은 패턴을 archive 큐에도 적용한 것.
- **고객 화면**: `GET /api/c/original-download`는 파일 수/총 용량/만료일/ZIP 상태와 URL이 없는 파일 메타데이터만 반환한다. ZIP 생성 중에는 `original_archive_parts.processed_file_count/processed_bytes`와 완료 파트 용량을 합산해 실제 장수·용량 진행률을 함께 반환한다. 워커는 DB 쓰기가 병목이 되지 않도록 최소 2초 간격(`ARCHIVE_PROGRESS_UPDATE_SECONDS=2`)으로 갱신한다. 고객 모달은 ZIP 기록 85% + R2 업로드 15% 가중치로 0~99%를 표시하고, 시작 후 실제 처리 속도가 확보되면 예상 남은 시간을 계산한다. 창을 닫아도 작업이 계속되고 사진 골라 받기는 즉시 가능함을 함께 안내한다. 파일 메타데이터에는 `selections.is_selected=true`를 기준으로 한 `isSelected`가 포함된다. 기존 활성 링크에 `original_archive_status=NULL`이면서 미완료 원본이 있는 레거시 상태는 `archiveBlocked=true`로 반환해 무한 "준비 중"이 아니라 미완료 장수와 작가 복구 필요를 안내한다. 실제 ZIP 준비 중일 때만 모달 닫힘 10초/열림 2초로 폴링한다. `GET /api/c/original-download/archive`는 ZIP 클릭 시, `POST /api/c/original-download/files`는 선택한 `photoIds` 다운로드 시에만 1시간 TTL presigned URL을 발급한다. 전체 원본은 ZIP 탭, 일부 원본은 개별 파일 탭으로 역할을 구분한다. 개별 파일 탭은 항상 전체 사진을 기본 목록으로 열고, 고객이 셀렉한 사진 수를 `내가 선택한 사진 모두 체크 N장`으로 표시한다. 이 체크박스를 켜면 고객 셀렉 사진만 다운로드 대상으로 추가하고, 끄면 해당 사진만 해제해 별도로 체크한 사진은 보존한다. 일부만 체크된 경우에는 체크박스를 중간 상태로 표시한다. 옆의 아이콘 전용 `다운로드 선택 초기화` 버튼은 고객 셀렉 여부와 관계없이 현재 다운로드 체크를 모두 비운다. 고객 셀렉 사진은 파일명 바로 뒤의 `선택됨` 뱃지로도 구분한다. 다운로드 체크 상태는 검색·폴링에 안전하도록 배열 인덱스가 아닌 `photoId`로 관리한다. 모바일에서 고객 셀렉 사진 일괄 체크와 기존 수동 체크의 합집합이 10장(`MOBILE_MAX_FILE_COUNT=10`) 또는 총 100MiB(`MOBILE_MAX_TOTAL_BYTES=100 * 1024 * 1024`)를 초과하면 일부만 체크하지 않고 전체 일괄 동작을 차단하며 이유별 안내를 표시한다. PC Chrome/Edge는 CTA 클릭 직후 `showDirectoryPicker()`로 폴더를 먼저 선택하고, API가 선택 ID 수와 동일한 URL을 반환했는지 확인한 뒤 각 URL 응답 body를 `FileSystemWritableFileStream`에 순차적으로 pipe한다. 동일 파일명이 이미 있으면 `(2)`, `(3)` 접미사로 보존한다. 이 경로는 자동 다중 다운로드 권한에 의존하지 않으며 한 번에 전부 Blob 메모리에 올리지 않는다. File System Access API 미지원 데스크톱 브라우저만 기존 `<a download>` 반복 방식으로 폴백한다. 모바일의 개별 수동 선택도 API가 이미 제공한 숫자형 `byteSize` 합계를 사용해 같은 두 제한을 먼저 초과하는 추가 선택을 즉시 차단한다. 문구는 기기 성능을 단정하지 않고 “휴대폰에서 안정적으로 저장하기 위한 기준”으로 안내하며 CTA 직전에도 두 제한을 재검증한다. Web Share가 정상 반환되거나 파일 다운로드 폴백을 실행한 뒤에는 다음 묶음을 고를 수 있도록 선택을 초기화하되, OS 사진 앱의 실제 저장 성공을 브라우저가 확인할 수 없으므로 별도 "저장 완료" 메시지는 표시하지 않는다. 모바일의 전체 압축파일 준비 완료 화면에는 용량이 큰 경우 원활한 다운로드를 위해 PC 이용을 권장하는 보조 문구를 표시하되 다운로드 자체는 차단하지 않는다.
- **기존 프로젝트**: 이 기능 배포 이전에 이미 활성화된 프로젝트는 `original_download_started_at`/`original_archive_status`가 `NULL`로 유지되어 소급 노출되지 않는다(신규 활성화 프로젝트부터만 적용).
- **최종 보정본과의 관계**: `OriginalDownloadEntry`의 촬영 원본과 `FinalDeliveryDownloadEntry`의 최종 보정본은 별도 기능이다. 최종 보정본은 `include_original`과 무관하게 필수 업로드하며, `delivered` 화면에서 최종 확정 회차 ZIP을 `delivered_at`부터 30일 동안 다운로드한다. 단일 ZIP은 별도 확인 모달 없이 즉시 다운로드하고, 용량 때문에 여러 ZIP으로 나뉜 경우에만 간결한 파일 선택 창을 표시한다. 재보정 요청 시 이전 후보 ZIP은 폐기되고 다음 검토 전송 때 다시 생성된다.

## 12. 클로즈드 베타 신청 및 관리자 심사(2026-07-26 추가, 2026-07-27 로그인 정책 변경)

`plan/beta-system.md`의 1~4단계 구현. 기존 "베타 등급"(§9-1 이용량 등급) 부여와는 별개로, 잠재 사용자를 모집·심사하기 위한 신청서 접수와 관리자 검토 화면이다.

### 12-1. 신청자(2026-07-27부터 로그인 필수)

- **시작 조건**: 랜딩페이지(`/landing`)의 베타 신청 CTA 또는 `/beta/apply` 직접 접근. **URL 자체는 로그인 여부와 무관하게 공개**이지만, 로그인 안 된 상태면 폼 대신 로그인 안내가 뜬다.
- **사용자가 수행하는 단계(로그인 안 된 경우)**: "로그인하고 신청하기" 클릭 → `AuthModal` 팝업(페이지 이동 없음)에서 구글/카카오 로그인(신규면 가입까지 한 번에 처리) → 완료되면 자동으로 다시 `/beta/apply`로 돌아와 이번엔 신청서 폼이 보인다.
- **사용자가 수행하는 단계(로그인된 경우)**: 이메일은 세션 값이 읽기 전용으로 이미 채워져 있고, 이름/휴대폰번호/촬영 장르/월평균 촬영 건수/프로젝트당 평균 전달 사진 수/현재 전달 방식/사용 희망 이유 입력 + 개인정보·연락 동의 체크 → "베타 신청하기".
- **프론트엔드 컴포넌트**: `src/app/beta/apply/page.tsx`(서버, 세션 이메일을 `BetaApplyForm`에 전달) + `src/components/beta/BetaApplyForm.tsx`(클라이언트 — `prefillEmail`이 없으면 로그인 안내 카드, 있으면 신청서 폼을 렌더).
- **로그인 후 원래 페이지로 복귀하는 방식**: `AuthModal`의 `redirectTo` URL에 `?next=...`를 붙이는 방법은 **Supabase의 Redirect URLs 허용 목록과 정확히 일치해야 해서 실제로 OAuth 콜백이 거부되는 문제가 있었다**(로컬 테스트에서 실측 — 에러와 함께 랜딩페이지로 튕김). 대신 로그인 시작 전 `sessionStorage`에 돌아갈 경로를 저장해두고(`src/lib/post-login-redirect.ts`), 로그인은 항상 기존 기본 목적지(`/photographer/dashboard`)로 완료된 뒤 그 페이지의 `useEffect`가 저장된 경로로 다시 이동시킨다. 기본 목적지 자체는 저장하지 않으며, 이전 버전에서 남긴 동일 경로 값도 복귀 대기로 취급하지 않고 소비한다. Supabase 프로젝트 설정은 전혀 건드리지 않는다. **대시보드 화면 깜빡임 방지(2026-07-27 추가, 2026-09-14 교착 방지 보완)**: `/photographer/dashboard`는 다른 페이지로 이동할 대기 값이 있을 때만 첫 렌더부터 실제 대시보드 콘텐츠 대신 로딩 화면을 보여준다. 현재 대시보드와 같은 값으로는 로딩을 유지하지 않는다.
- **호출되는 API**: `POST /api/beta/applications` — **2026-07-27부터 세션 필수**(없으면 401). 휴대폰번호는 `src/lib/phone.ts`로 정규화 후 저장, 서버가 중복 여부를 조회해 이미 등록된 번호면 409로 거부한다. 이메일/`matched_photographer_id`는 항상 서버가 세션에서 가져온 값 — 클라이언트가 이메일을 보내는 경로 자체가 없다.
- **성공 시 기대 결과**: `/beta/apply/complete`로 이동, "신청이 접수되었습니다" 안내. `matched_photographer_id`는 제출 즉시 채워져 있다(별도 매칭 단계 불필요).
- **실패 및 경계 상황**: 필수 항목 누락/형식 오류는 클라이언트에서 우선 차단, 서버도 동일 항목을 재검증한다. 같은 번호로 재신청 시 신규 레코드를 만들지 않고 안내 문구를 표시한다(레이스 컨디션은 `phone` 컬럼의 `UNIQUE` 제약이 최종 방어).
- **관련 권한/인증 조건**: 페이지 라우팅 자체는 게이트 없음(`middleware.ts`의 matcher가 `/beta/**`를 포함하지 않음) — 대신 화면 렌더링과 제출 API가 각자 세션 유무로 분기한다.
- **QA에서 확인해야 할 항목**: 로그인 상태에서 제출 시 이메일이 실제로 세션 값으로 저장되는지(실 데이터로 확인 완료), 신규 OAuth 가입(브랜드뉴 계정)을 통한 라운드트립은 실제 신규 계정이 없어 코드 리뷰 수준으로만 확인(기존 계정 재로그인 경로는 실측 완료).

### 12-2. 관리자(`/admin/beta-applications`)

- **시작 조건**: 관리자 계정으로 로그인 후 사이드바 "Beta Applications" 메뉴 진입(`admin-nav.ts`).
- **사용자가 수행하는 단계**: 목록에서 상태 필터(`?status=`)/이름·번호 검색(`?q=`, GET 쿼리스트링 기반) → 신청자 클릭 → 상세에서 상태(신청완료→검토중→승인/보류/거절) 변경, 연락완료 체크, 관리자 메모 저장.
- **프론트엔드 컴포넌트**: `src/app/admin/beta-applications/page.tsx`(목록), `src/app/admin/beta-applications/[id]/page.tsx`(상세) + `src/components/admin/AdminBetaApplicationControl.tsx`(상태/메모/연락완료 저장, 기존 `AdminFeedbackStatusControl`/`AdminBetaControl` 패턴과 동일하게 `fetch` PATCH 후 `router.refresh()`).
- **호출되는 API**: `PATCH /api/admin/beta-applications/[id]` — `getAdminUser()` 재검증 후 상태/메모/연락완료를 부분 업데이트.
- **성공 시 기대 결과**: 변경 즉시 반영(페이지 refresh). 신청이 로그인 필수가 되면서 `matched_photographer_id`는 항상 채워져 있으므로 상세 화면 상단에 "이미 가입된 계정과 매칭됨" 배지가 항상 표시되고 `/admin/users/[id]`로 링크된다.
- **실패 및 경계 상황**: 승인 상태로 바꿔도 `photographers.beta_status` 변경은 자동으로 일어나지 않는다(의도된 설계 — §9-1과 별개 축, plan/beta-system.md §4 참고) — 대신 아래 12-3의 "베타 부여" 버튼으로 명시적으로 처리한다.
- **관련 권한/인증 조건**: `middleware.ts`의 `/admin`, `/admin/:path*` matcher가 이미 이 라우트를 포함하므로 별도 인증 코드를 추가하지 않았다 — 비관리자 계정으로 접근하면 `/photographer/dashboard`로 리다이렉트됨을 실제로 확인함.
- **QA에서 확인해야 할 항목**: 상태 필터/검색이 여러 항목을 동시에 조합했을 때도 정확한지, 신청자 수가 늘어난 뒤에도 목록 페이지 성능이 괜찮은지(현재는 페이지네이션 없이 전체 조회).

### 12-3. 승인 사용자·가입 연결(2026-07-26 초안, 2026-07-27 재설계)

신청이 로그인 선행 조건이 되면서(§12-1) `matched_photographer_id`가 항상 이미 채워져 있다 — "가입 전 이메일 사전등록"(`beta_invitations`) 방식은 신청자가 이미 가입돼 있는 상황과 안 맞아(호출하면 항상 "이미 가입된 사용자입니다" 거부) 폐기하고, 이미 존재하는 계정에 직접 베타를 부여하는 단순한 흐름으로 다시 설계했다.

- **시작 조건**: 신청 상태를 `approved`로 바꾼 뒤, 매칭된 계정이 아직 베타가 아니면(`beta_status !== 'active'`) 상세 화면에 "가입 연결" 카드와 "베타 부여" 버튼이 노출됨.
- **사용자가 수행하는 단계**: "베타 부여" 클릭 → 기존 `PATCH /api/admin/users/[id]/beta`를 그대로 재사용해 `{beta_status:'active'}`만 전송. 날짜를 직접 보내지 않으면 서버가 `app_settings.beta_default_duration_days`만큼(기본값 30일) 오늘부터 자동으로 `beta_start_date`/`beta_end_date`를 채운다(2026-07-27부터, 이전에는 날짜를 비워둬 무기한 유효로 처리했음). 다른 기간을 쓰려면 이후 `/admin/users/[id]`의 `AdminBetaControl.tsx`에서 명시적으로 날짜를 지정해 재저장하면 된다(날짜를 직접 보내는 요청은 자동 채움 대상이 아니라 그대로 저장됨).
- **프론트엔드 컴포넌트**: `src/components/admin/AdminBetaApplicationControl.tsx` — "이메일로 수동 매칭" 입력창은 완전히 제거됨(2026-07-27, 신청 시점에 항상 자동 매칭되므로 더 이상 필요 없다고 판단, 예외 상황용 폴백도 의도적으로 남기지 않음).
- **성공 시 기대 결과**: `router.refresh()` 후 버튼이 사라지고(이미 베타 상태이므로), `/admin/users/[id]`에서도 베타 상태 변경이 확인된다.
- **실패 및 경계 상황**: `matched_photographer_id`가 비어 있는 경우(정상 흐름에서는 로그인 필수라 발생하지 않음 — 이 정책 이전의 레거시 데이터 등 예외 상황에서만 가능)는 버튼 대신 "매칭된 계정이 없습니다" 경고 문구만 표시하고, 관리자가 Supabase 대시보드에서 직접 확인해야 한다(별도 UI 미제공).
- **관련 권한/인증 조건**: `PATCH /api/admin/users/[id]/beta`는 `getAdminUser()` 재검증.
- **QA에서 확인해야 할 항목**: "베타 부여" 버튼 클릭 → `photographers.beta_status`가 실제로 `active`로 바뀌는지 실 데이터로 확인 완료(테스트 후 원래 상태로 복구함). 신규 가입(브랜드뉴 OAuth 계정 생성)을 통한 §12-1의 "가입 시점 자동 매칭" 백필 로직만 실제 신규 계정이 없어 코드 리뷰 수준으로만 확인했다.

### 12-4. 핵심 사용 행동 집계(2026-07-27 추가)

- **시작 조건**: 없음(자동) — 신청자가 실제로 가입하거나, 그 작가의 고객이 링크에 접속하는 시점에 자동으로 기록된다. 관리자가 직접 트리거하는 동작이 아니다.
- **사용자가 수행하는 단계**: 없음. (a) 신규 사용자가 OAuth로 가입, (b) 로그인(신규/기존 모두), (c) 고객이 `/c/[token]` 링크를 클릭 — 3가지 자연스러운 행동이 곧 트리거다.
- **기록 지점**: `src/app/auth/callback/route.ts`에서 `signup_completed`(신규 가입 시 1회)와 `first_login`(신규/기존 가입 모두, 작가당 최초 1회)을, `src/app/c/[token]/layout.tsx`(인덱스 `page.tsx`가 아니라 모든 하위 경로를 감싸는 layout — `/gallery` 등 딥링크 진입도 놓치지 않기 위해)에서 `customer_link_visited`(프로젝트당 최초 1회)를 기록한다. 셋 다 `src/lib/beta-usage-events.ts`의 `recordBetaUsageEvent()`를 공유하며 이 함수는 절대 throw하지 않는다 — 이벤트 기록 실패가 로그인/고객 접속 자체를 막지 않는다.
- **성공 시 기대 결과**: `/admin/beta-applications/[id]`에서 매칭된 계정이 있으면 "사용 현황" 섹션(첫 로그인 시각/생성한 프로젝트 수/고객이 접속한 프로젝트 수)이 노출된다. 프로젝트 생성 수는 기존 `projects` 테이블을 그대로 카운트하는 것이라 별도 이벤트 기록이 필요 없다(plan/beta-system.md §6.1에서 이미 "이미 확보 가능"으로 분류됨).
- **실패 및 경계 상황**: 같은 작가가 여러 번 로그인해도 `first_login`은 부분 유니크 인덱스(`photographer_id, event_type WHERE project_id IS NULL`)로 1건만 남는다. 같은 고객이 링크를 여러 번 열어도 `customer_link_visited`는 프로젝트당 1건만 남는다(`project_id, event_type WHERE project_id IS NOT NULL`). 두 경우 모두 두 번째 이후 insert는 유니크 위반(23505)으로 조용히 무시되므로 매번 "이미 기록됐는지" 조회하지 않는다.
- **관련 권한/인증 조건**: 없음(로그인/고객 접속 경로에 자동으로 끼워짐). 관리자 화면 표시만 `getAdminUser()` 보호 대상.
- **QA에서 확인해야 할 항목**: 신규 OAuth 가입을 통한 `signup_completed`/`first_login` 기록은 §12-3과 동일한 이유로 아직 실측하지 못했다(코드 리뷰 수준) — 다음에 실제 신규 계정 가입이 발생하면 확인 필요. `customer_link_visited`는 2026-07-27 마이그레이션 적용 후 실제 고객 링크(`/c/[token]/gallery` 딥링크 포함)로 검증 완료 — 최초 방문 시 정확히 1건 기록되고, 같은 링크 재방문(새로고침) 시에도 중복 없이 1건만 유지됨을 확인했다. 관리자 상세 화면의 "사용 현황"(생성한 프로젝트 수·고객 접속 프로젝트 수)도 실 데이터와 정확히 일치함을 확인했다.

### 12-5. 베타 설문 — ②첫 프로젝트 납품 완료 후(2026-07-27 추가, 5단계)

- **시작 조건**: 작가가 `/photographer/dashboard`에 진입했고(프로젝트가 1개 이상 있어야 함), 그 작가의 **첫 생성 프로젝트**(생성일 기준, 납품일 기준 아님)가 `status='delivered'`인 상태.
- **사용자가 수행하는 단계**: 별도 수행 없이 조건 충족 시 대시보드에 모달이 뜬다(`BetaSurveyModal`). 5문항(①실제 고객 사용 여부(예/아니오) ②시간 절감 체감(1~5점) ③가장 도움이 된 기능(복수선택+기타) ④가장 불편했던 점(자유서술) ⑤다음 프로젝트에서도 사용할 계획(1~5점, 조기 이탈 예측) — 2026-07-27 재설계, plan/beta-system.md §7.1a) 응답 후 "제출", 또는 "나중에"(24시간 뒤 재노출), 또는 "다시 묻지 않기"(영구 재노출 안 함) 중 하나를 선택한다.
- **컴포넌트/API**: `src/app/photographer/dashboard/page.tsx`가 마운트 후 `GET /api/photographer/beta-survey/status`로 노출 여부를 확인한다. 트리거 판정은 서버가 `projects` 테이블에서 `photographer_id`의 최초 생성 프로젝트 status를 직접 조회한다(생성 순서 기준 판정이므로 납품 시각은 사용하지 않음). 응답/나중에는 `POST /api/photographer/beta-survey`, 건너뛰기는 `POST /api/photographer/beta-survey/skip`이 처리하며 `beta_survey_responses` 테이블(`photographer_id, survey_type` 유니크)에 upsert된다.
- **성공 시 기대 결과**: 제출/건너뛰기 후에는 몇 번을 재방문해도 다시 뜨지 않는다. "나중에" 후에는 24시간 동안만 재노출이 억제되고 이후 다시 뜬다. "노출" 자체는 별도로 기록하지 않으므로, 세 시각(`later_until`/`skipped_at`/`submitted_at`) 중 아무것도 없는 상태에서 조건이 계속 켜져 있으면 대시보드 방문마다 다시 뜬다(설계상 의도 — §7.2 "1회 노출"은 "영구 1회"가 아니라 "이번 방문에 1회").
- **실패 및 경계 상황**: 이미 제출된 설문에 다시 제출 요청이 오면(중복 클릭 등) 서버가 멱등 처리(`alreadySubmitted:true`, DB 재기록 없음). 복수선택 문항(③가장 도움이 된 기능)에서 "기타"를 골랐는데 텍스트를 안 채우면 클라이언트/서버 양쪽에서 막고, 최소 1개 선택도 서버가 강제한다. 빈 대시보드(`projects.length === 0`)에서는 트리거 자체가 구조적으로 성립할 수 없어 이 상태를 위한 별도 분기는 없다.
- **관련 권한/인증 조건**: `api/photographer/beta-survey/*` 세 엔드포인트 모두 세션 필요(401 없으면). `admin_audit_logs`에는 기록하지 않는다 — 그 테이블은 관리자/시스템 행위 전용이고(§10-1), 작가가 자발적으로 제출하는 설문은 기존 `feedback` 제출과 동일하게 감사 로그 대상이 아니다.
- **범위 밖**: ①"셀렉 링크 전달 후" 설문은 문항이 아직 확정되지 않아(plan/beta-system.md §7.1, §13) 트리거·문항을 구현하지 않았다. `src/lib/beta-survey.ts`의 `SurveyType`에 식별자(`link_sent`)만 미리 선언해뒀고, `IMPLEMENTED_SURVEY_TYPES`에는 아직 넣지 않았다.
- **QA에서 확인해야 할 항목**: `tests/e2e/photographer/beta-survey.spec.ts`에서 트리거 미충족 시 미노출/충족 시 노출/나중에 24h 정책/건너뛰기 영구 억제/제출 후 영구 억제/미인증 401을 다룬다. `src/app/api/auth/test-setup/route.ts`에 테스트 전용 액션(`first_project_status`/`set_project_status`/`reset_beta_survey`/`backdate_survey_later`)을 추가해 실제 촬영→선택→납품 워크플로우를 거치지 않고도 상태를 직접 조작해 검증할 수 있게 했다(`ENABLE_TEST_LOGIN=true`일 때만 동작, 기존 `create_project` 등과 동일한 안전장치). DB 마이그레이션(`20260727_beta_survey_responses.sql`) 적용 후 실 브라우저(Playwright)로 6개 시나리오 모두 통과 확인 완료(2026-07-27).

### 12-6. 베타 설문 — ③두 번째 프로젝트 납품 완료 후(2026-07-27 추가, 6단계)

- **시작 조건**: 작가가 `/photographer/dashboard`에 진입했고, **생성 순서 기준 두 번째 프로젝트**(완료 순서 아님, plan/beta-system.md §6.1)가 `status='delivered'`인 상태. ②와 마찬가지로 이미 제출/건너뛰기했으면 트리거되지 않는다.
- **사용자가 수행하는 단계**: 조건 충족 시 대시보드에 모달이 뜬다. 8문항(①계속 사용 의향(1~5점) ②추천 의향 NPS(0~10) ③서비스가 없어진다면 얼마나 아쉬울지(1~5점, PMF/Sean Ellis 문항) ④적정 가격(구간 선택) ⑤유료 출시 시에도 계속 사용할 의향(1~5점) ⑥추가되었으면 하는 기능(자유서술) ⑦기타 의견(자유서술) ⑧정식 출시 안내 희망 여부(체크박스) — 2026-07-27 재설계, plan/beta-system.md §7.1a) 응답 후 "제출", 또는 "나중에", 또는 "다시 묻지 않기" 중 하나를 선택 — 노출/재노출 정책은 ②와 완전히 동일(§7.2).
- **컴포넌트/API**: ②와 동일한 인프라를 그대로 재사용 — `GET .../beta-survey/status`가 `IMPLEMENTED_SURVEY_TYPES`(생애주기 순서로 5개 타입 등록, §12-7 참고)를 순서대로 검사해 먼저 트리거된 것을 반환하고(모든 설문은 `(photographer_id, survey_type)`별로 완전히 독립적으로 상태 관리됨), `BetaSurveyModal`은 `surveyType` 값에 따라 문항 블록만 분기한다. 트리거 판정은 ②와 동일하게 `projects.status`를 직접 조회(두 번째로 생성된 행을 `ORDER BY created_at ASC` + `range(1,1)`로 특정) — `project_logs.action='delivered'`는 신뢰하지 않는다(②와 동일 이유, §12-5).
- **"적정 가격" 문항 형식**: 문서(plan/beta-system.md §7.1)에 "주관식/구간 선택" 둘 다 언급돼 있어 확정이 필요했음 — 사용자 확인 후 **구간 선택**으로 결정. 최초 구현("무료가 아니면 안 씀/1만원 미만/1만원~3만원/3만원~5만원/5만원 이상")은 같은 날 문항 재설계에서 "무료 아니면 안 씀"이 너무 공격적이라는 피드백을 받아 **월 5천원 미만/5천원~1만원/1만원~3만원/3만원~5만원/5만원 이상/현재로서는 유료 이용 의향 없음**(마지막으로 이동)으로 최종 확정했다. 구간 경계값은 하드코딩이라 나중에 바꾸려면 `src/lib/beta-survey.ts`/`BetaSurveyModal.tsx`/API 검증 로직 3곳을 함께 수정해야 한다.
- **성공 시 기대 결과 / 실패 및 경계 상황 / 권한**: §12-5와 동일 — 멱등 제출, 세션 필수(401), `admin_audit_logs` 미기록.
- **QA에서 확인해야 할 항목**: `tests/e2e/photographer/beta-survey.spec.ts`의 두 번째 `describe` 블록(CS1~CS5)에서 트리거 미충족/충족/나중에 24h/건너뛰기 영구 억제/NPS·가격 구간·체크박스 포함 제출까지 실 브라우저로 검증 완료(2026-07-27). 테스트 계정에 두 번째 프로젝트가 없으면 `test-setup`의 `second_project_status` 액션이 테스트용으로 하나 생성하고, 테스트 종료 후 새로 만든 경우에 한해 삭제한다(`tests/helpers/setup.ts`의 `getSecondProjectStatus`/`deleteTestProject`) — 기존에 있던 프로젝트를 건드린 경우는 원래 status로 복원만 한다.

### 12-7. 베타 설문 — 첫 프로젝트 진행 중 마이크로 설문 3종(2026-07-27 추가)

- **배경**: ②③가 프로젝트가 "끝난 후"에만 몰려 있어 실사용 중 막히는 지점을 실시간으로 파악하기 어렵다는 문제 제기 — 상태 전이마다 설문을 넣으면 응답률이 떨어지므로, 첫 프로젝트 진행 중 딱 3개 지점에만 1~2문항짜리 마이크로 설문을 추가했다. "10초 안에 답할 수 있는" 것이 핵심 제약이며, 인프라(테이블/모달 셸/API 3종/노출정책)는 ②③와 100% 동일하게 재사용한다.
- **시작 조건 3종**:
  - `project_created`: 작가의 첫 프로젝트가 존재하는 시점(사실상 대시보드가 빈 상태를 벗어나는 시점).
  - `original_uploaded`: 첫 프로젝트에 `project_logs.action='uploaded'` 이벤트가 최소 1건 존재하는 시점(`src/app/photographer/projects/[id]/upload/page.tsx`에서 업로드 배치가 끝날 때마다 기록 — 여러 번 있을 수 있어 "최소 1건"으로 판단).
  - `selection_received`: 첫 프로젝트에 `project_logs.action='confirmed'` 이벤트가 존재하는 시점(`src/app/api/c/confirm/route.ts`에서 고객이 선택 확정 시 기록). ②③와 달리 `projects.status`가 아니라 **로그 존재 여부**로 판단한다 — 고객이 이후 `cancel-confirm`으로 확정을 취소하면 status는 `selecting`으로 되돌아가지만, "회신받았다"는 사실 자체는 이미 일어난 이벤트이기 때문이다.
- **사용자가 수행하는 단계**: 조건 충족 시 대시보드에 모달이 뜬다. 문항(§7.1a): 생성 후(1문항, 생성 과정 난이도 1~5점), 원본 업로드 후(2문항, 업로드 수월함 1~5점 + 불편한 점 자유서술), 셀렉 회신받았을 때(2문항, 확인 과정 편리함 1~5점 + 고객 피드백 자유서술). "제출"/"나중에"/"다시 묻지 않기" 3가지 액션은 ②③와 동일(선택 즉시 자동제출 아님 — 사용자 확정).
- **컴포넌트/API**: `IMPLEMENTED_SURVEY_TYPES`가 생애주기 순서로 `["project_created","original_uploaded","selection_received","first_delivery","second_delivery"]`로 확장돼, 여러 개가 동시에 조건 충족돼도 가장 이른 것부터 노출된다. 세 타입 모두 첫 프로젝트를 `project_id` 컨텍스트로 저장(기존 `getFirstProjectId` 재사용).
- **DB 마이그레이션**: `20260727b_beta_survey_responses_add_micro_types.sql` — `survey_type` CHECK 제약을 6개 값으로 확장. 적용 완료(2026-07-27).
- **⚠️ 재노출 관련 중요 차이점**: ②③의 트리거는 `projects.status`(복원 가능한 필드)에 의존하지만, 이 3종의 트리거는 "프로젝트 존재"·"로그 존재"라는 **되돌릴 수 없는 사실**에 의존한다. 즉 한 번 트리거되면(프로젝트 1개만 있어도) 사용자가 직접 응답하거나 "다시 묻지 않기"를 누르기 전까지 대시보드 방문마다 계속 노출된다(§7.2 설계상 의도 — "나중에"는 24시간만 억제). E2E 테스트에서 이 특성 때문에 `beta_survey_responses` 행을 삭제(reset)하는 정리 방식이 다른 e2e 스펙(`dashboard.spec.ts`)의 대시보드 클릭을 실제로 가로막는 회귀를 일으켰다 — 테스트 종료 후에는 삭제 대신 영구 skip으로 남기도록 수정했다.
- **실패 및 경계 상황 / 권한**: §12-5와 동일 — 멱등 제출, 세션 필수(401), `admin_audit_logs` 미기록.
- **QA에서 확인해야 할 항목**: `tests/e2e/photographer/beta-survey.spec.ts`의 3개 신규 `describe` 블록(PS1, US1~US2, SS1~SS2)에서 노출·문항 렌더·제출·나중에·다시 묻지 않기를 검증 완료(2026-07-27). `test-setup`의 `insert_project_log` 액션으로 실제 업로드/셀렉 확정 플로우 없이 이벤트를 직접 삽입해 트리거를 테스트한다. **"트리거 미충족 → 미노출" 부정 케이스는 검증하지 않았다** — 이 계정의 첫 프로젝트엔 이미 실사용/QA 이력이 쌓여 있어 project_logs가 append-only라 지울 수 없고, 안전하게 "로그 없음" 상태를 재현할 수 없기 때문(②③의 BS1/CS1과 다른 점).

- 설정의 도움말에서 사용 매뉴얼과 기존 문의하기 창을 연다. 모바일 매뉴얼 접근을 허용하고 Dashboard 모바일 목록 redirect는 유지한다.
- 원본 업로드의 선택 버튼/길게 누르기 → 전체 선택·해제/취소 → 선택 삭제 확인 순으로 관리한다. 같은 gesture의 release가 이웃 사진을 추가 선택하지 않는다.
- PC 원본 포함 업로드는 세션 중 실제 전송 처리량에 맞춰 대기 중 원본의 동시 전송 수를 자동 조절하고, 미리보기 준비에는 기기 사양에 따라 2~3개 압축 worker를 사용한다. 사용자가 별도로 설정할 항목은 없으며 진행률·남은 시간·중단·실패 원본 재시도 흐름은 유지한다. 모바일은 메모리와 회선 안정성을 위해 압축과 전송을 각각 1개로 유지한다.
- 모바일 보정본은 PC 공용 카드의 2열 갤러리가 기본이며, 필요하면 사진 작업 더보기에서 목록으로 전환한다. 하단에 업로드 수와 검토 요청 가능 조건을 표시하고 첫 방문 업로드창을 닫아도 toolbar로 재진입한다.
- 시트·업로드창·문의·사진 뷰어는 배경 조작 차단과 focus 복귀를 공유한다. API의 상태 전환 조건은 변경하지 않았다. [구현과 검증 범위](mobile-design-implementation-2026-09-09.md).

모바일 보정 화면 후속 개선: 상단 고객명을 생략하고 프로젝트명·상세 복귀를 유지한다. 상단 도구줄은 필터/정렬과 보기 전환만 공통 아이콘 버튼으로 표시하며, 중복되는 일괄 업로드와 단계·전체 장수 요약은 표시하지 않는다. 모바일 보정본 내보내기도 제거했다. 개별 업로드는 각 원본에 대응하는 ‘파일 선택’ 버튼이며 선택 즉시 업로드 계약은 유지한다. 현재 보정 단계의 업로드가 남아 있는 동안 하단 Primary 버튼이 `일괄 업로드`로 안내하며, 전체 업로드 완료 후 검토 요청 흐름으로 바뀐다.

모바일 일괄 업로드 창은 반복 안내를 줄인다. 56px header에는 `보정본 업로드`와 닫기만 표시하고, 대상·새 파일·매칭 상세와 별도 `매칭 결과` 제목은 숨긴다. 기존 보정본이 있으면 52px file selection bar에서 `선택/전체 장수 · 용량`과 `파일 다시 선택`만 제공하며, 부분 업로드는 `선택한 N장만 업로드됩니다.` 한 줄로 안내한다. 자동 매핑 원리와 비활성 업로드 버튼 위의 `추가로 업로드할 파일을 선택해주세요.` 문구를 숨기고, 펼침 항목은 `사진별 선택`으로 축약한다. 사진별 연결 목록은 원본과 보정본 한 쌍을 하나의 card로 묶고, 양쪽에 한 줄 파일명과 같은 크기의 4:3 preview를 그 순서로 표시한다. AI의 1·2위 후보 점수 차이가 작으면 연결과 업로드를 막지 않고 `AI 확인 필요`로 표시한다. 보정본 preview 우측 상단 모서리의 작은 Danger `X`는 해당 연결을 삭제하며, 삭제 후 나타나는 `파일 선택` surface에서 새 보정본을 선택한다. 별도 변경 CTA는 표시하지 않는다. 삭제 확인은 제목·복구 불가 안내·취소·삭제만 표시한다.

### 모바일 보정 목록의 비교·선택 동작 (2026-09-09)

- 원본과 업로드된 보정본 중 어느 사진을 눌러도 해당 쌍을 기존 상세 뷰어에서 비교한다. 아직 보정본이 없으면 원본 상세를 표시한다. 양쪽 파일명을 보고 연결을 확인할 수 있다.
- 삭제할 사진은 사진 작업 더보기 → 보정본 선택으로 선택 모드에 들어가 지정한다. 전체 선택/해제와 취소를 제공하며, 선택 후 기존 선택 삭제·확인 흐름으로 이어진다. 확정된 보정본을 선택할 수 없는 기존 조건을 유지한다.
- 점선 슬롯에서 파일을 선택하면 해당 원본에 즉시 업로드한다. 하단에서 완료 수량과 검토 요청까지 필요한 업로드/교체 수량을 확인한다. 검토 요청 조건 및 서버 상태 전환은 변경하지 않았다.

보정 갤러리 카드에는 코멘트를 표시하지 않는다. 셀렉 상세보기에는 해당 사진의 셀렉 단계 코멘트만 표시한다. 보정 상세보기에는 현재 보고 있는 작업 회차가 `revision_requested`인 경우에만 그 회차의 재보정 요청 코멘트를 표시한다. 셀렉 코멘트, 확정된 회차의 코멘트, 과거 버전 코멘트를 전체 이력으로 합쳐 노출하지 않으며 현재 단계에 표시할 코멘트가 없으면 코멘트 영역도 만들지 않는다. 코멘트 저장·검토 상태 전환 동작은 변경하지 않았다.

모바일 갤러리는 2열을 유지한다. 각 카드 상단 좌측의 작은 원본 thumbnail을 누르면 원본 상세가 열리고 우측에는 파일 정보를 표시한다. 업로드 전에는 PC·모바일 모두 원본 파일명 하나만 표시하며 `미업로드` 배지는 사용하지 않는다. 업로드 후에는 보정본 파일명과 `원본 · 파일명` 보조 정보를 표시한다. 그 아래 큰 보정본 preview를 누르면 현재 회차 상세가 열린다. 체크·교체 action은 보정본에만 적용된다. 회차 선택은 필터·보기 도구와 같은 줄의 선택 메뉴로 제공한다. PC는 같은 정보 위계와 고해상도 대응 보정 preview를 유지하고 상태 필터에만 수량을 표시한다. 업로드·검토 요청은 보고 있는 회차에 대응한다. 재보정 작업 중 1차 보정 탭은 `1차 보정 검토 완료`만 표시하며, 재보정 탭으로 전환해야 해당 업로드·검토 요청을 실행할 수 있다. 업로드 완료 안내는 `보정본 N장 준비 완료`로 축약한다.

### 모바일 보정 상세의 보기 전환·이력·코멘트

보정 상세 상단에서 원본/보정본을 직접 전환한다. Desktop 버전 이력에서는 원본·현재·이전 보정 버전을 탐색할 수 있지만, 코멘트는 이력에 종속하지 않고 현재 작업 회차가 재보정 요청 상태일 때의 요청 내용만 표시한다. 모바일에서는 나란히 비교를 숨기고 버전 이력을 버전명·상태 중심의 짧은 목록으로 표시한다. 사진 이동은 보기 모드를 유지하며 보정본이 없는 사진에서는 미업로드 상태를 안내한다.


### 모바일 상세 사진 집중 보기와 조작부 정리

모바일 보정 상세에서 사진을 한 번 탭하거나 집중 보기 버튼을 누르면 헤더·보기 전환·하단 정보·썸네일·이동 버튼이 접힌다. 사진을 다시 탭하거나 조작 메뉴 보기 버튼을 누르면 복원된다. 공용 `MobileViewerPinchPhoto`를 재사용해 핀치 확대/팬과 더블 탭 확대·초기화를 지원하며 더블 탭에는 집중 보기 토글이 실행되지 않는다. PC 뷰어와 업로드 데이터 흐름은 바뀌지 않는다.


### 모바일 비교 탭·집중 보기 CTA 제거

후속 요청으로 모바일 상세 뷰어는 원본·보정본 두 가지 전환만 제공한다. 비교 상태로 진입해도 모바일에서는 해당 사진 한 장을 표시하고 보정본 버튼을 활성화한다. PC 비교 기능은 유지한다. 집중 보기 CTA와 해당 버튼용 상단 여백을 제거했으며, 사진 단일 탭으로 조작 영역을 숨기고 다시 탭해 복원하는 동작 및 핀치·더블 탭 확대는 유지한다. 이전 절의 비교 탭·집중 보기 버튼 설명은 이 변경으로 대체된다.


### 모바일 버전 이력 아이콘과 중앙 이동 버튼

모바일 상세의 버전 이력 CTA는 제거했다. 이전/다음 버튼은 사진 영역의 좌우 세로 중앙에 배치하며 44px 터치 영역을 유지한다. PC 버전 이력과 데이터/API 흐름은 유지한다.


### 모바일 코멘트 직접 표시

코멘트 개수·진입 화살표·별도 코멘트 시트를 제거하고 현재 단계에 해당하는 본문을 바로 표시한다. 셀렉 상세보기는 `셀렉 코멘트`, 보정 상세보기는 현재 회차가 재보정 요청 상태일 때 `재보정 요청`만 표시한다. 두 화면은 같은 `ViewerCommentPanel`의 청록색 인용선과 본문 규격을 공유하지만 서로 다른 단계의 코멘트를 합치지 않는다. 표시할 코멘트가 없으면 빈 상태 문구와 패널을 모두 숨긴다. 긴 코멘트는 모바일 패널 안에서 스크롤하며 더 보기/접기 단계를 거치지 않는다.


### 모바일 상세 미업로드·탭 개선 1~14

모바일 보정본 미업로드 시 원본을 대체 표시하지 않고 공용 ACUT 로고와 안내를 표시한다. 보정본 모드는 유지하며 원본 탭 및 좌우/썸네일 탐색은 계속 사용할 수 있다. 미업로드 배지는 보정본 모드 썸네일에만 나타나고 원본만 있는 이력 시트는 상태를 안내한다. 코멘트 출처, 간결한 모드 컨트롤, 고정된 헤더·사진 프레임을 적용했다. ViewerMobileImage는 URL별로 로딩/완료/실패 상태를 관리하며 이전 사진을 새 보정본처럼 표시하지 않는다. API·업로드·PC 비교 흐름은 유지한다. 세부 번호별 규격은 design-system-light.md의 모바일 상세 뷰어 미업로드·탭 개선 1~14 절을 따른다. 이전 원본 대체 표시 설명은 이번 구현으로 대체된다.


### 모바일 보정본 전체 선택과 하단 삭제

보정본 목록의 `보정본` 컬럼 헤더 앞 체크박스로 현재 목록에서 삭제 가능한 보정본을 전체 선택하거나 해제한다. 체크박스와 컬럼명 묶음은 보정본 파일명의 왼쪽 시작선에 맞춘다. 일부만 선택된 상태는 중간 상태 체크박스로 표시한다. 모바일 상단 작업 도구줄에는 현재 보정 단계·전체 장수·삭제 CTA를 표시하지 않는다. 한 장 이상 선택하면 하단 공용 작업 바가 선택 장수와 Primary `선택 삭제`를 제공한다. 선택을 모두 해제하면 기존 업로드 현황과 검토 요청 행동으로 돌아간다. 삭제 버튼은 기존 확인 창을 연 뒤에만 삭제를 실행하며, 확정 보정본과 미업로드 항목은 선택 대상에서 제외한다. 고객 검토 중에는 선택 UI와 삭제 action 전체를 표시하지 않는다.


### 모바일 보정본 카드 기본 보기 (2026-09-10)

모바일 보정본 탭은 PC와 같은 보정 카드의 2열 갤러리를 기본으로 연다. 업로드 전 카드 헤더는 원본 참조 thumbnail과 원본 파일명만 표시하고 PC·모바일 모두 `미업로드` 배지를 두지 않는다. 업로드 후에는 보정본 파일명과 원본 보조 정보, 가로형 보정본을 표시한다. 갤러리 코멘트는 생략하며 목록 보기와 상세보기에는 현재 회차에서 재보정 요청된 항목의 코멘트만 표시한다. 원본·보정본을 행 단위로 비교하는 목록 보기는 `사진 작업 더보기`에서 계속 전환할 수 있다.

갤러리 상단의 `전체` 체크박스는 현재 필터에서 삭제 가능한 업로드 보정본을 전체 선택한다. 각 업로드 카드에서는 보정 이미지 좌측 상단 체크박스로 개별 선택을 조정하며 파일명 행을 밀지 않는다. 확정 보정본과 미업로드 카드에는 체크박스를 표시하지 않는다. 선택하면 상단 삭제 CTA 없이 하단 작업 바에 선택 장수와 주황색 `선택 삭제 N장` 버튼만 표시한다. 별도 선택 해제 CTA는 두지 않고 선택된 카드나 전체 체크박스를 다시 눌러 해제한다. 삭제 확인 절차는 유지한다. 이 절은 앞 절의 목록 기본 진입 설명을 대체하고, 목록을 선택했을 때의 컬럼 헤더 전체 선택 동작은 유지한다.

## 03 검토 영상 적용 (2026-09-12)

### 자산 탭 작업 도구 개선

- 상세 뷰어의 사진 배경은 어두운 중립색을 유지하고 헤더·정보 패널까지 다크 톤을 사용하며 밝은 회색 본문으로 대비를 확보한다. 셀렉 PC는 요청이 없어도 패널 폭을 유지한다. 보정본은 현재 버전·상태와 그 버전의 코멘트를 먼저 보여주고, 비교와 버전 이력을 이어서 표시한다. 모바일 보정본은 사진 아래 현재 버전·상태를 표시하고 요청·이력을 펼쳐 확인한다. 기존 사진 이동·확대·원본 비교 동작을 유지한다.

- 셀렉·보정본 카드의 코멘트는 두 줄까지 노출하고 사진 클릭으로 해당 사진의 기존 뷰어를 연다. 보정본 카드에서 확정·재보정 요청·검토 상태를 구분하며, 재보정 요청 필터를 확정보다 먼저 배치한다. 상태 변경 API와 검토 처리 규칙은 유지한다.

- 원본·셀렉·보정본·최종본은 공통 밑줄형 탭과 반응형 도구줄을 사용한다. PC 스크롤에서는 프로젝트 정보만 접고 탭·도구는 유지한다. 모바일도 도구를 숨기는 몰입 모드 대신 유지한다.

- 상단 경로에는 프로젝트 이름을 표시하며 상세페이지로 돌아가는 동작을 유지한다. 납품용 원본을 포함하지 않는 설정은 ‘셀렉용 사진만 전달’로 안내한다.

### PC 대시보드 작업 중심 구성

- `DashboardOverview`가 우선 작업 최대 5건을 표시한다. 기존 `getFocusRankedProjects()` 우선순위는 유지하며 첫 프로젝트는 1:1 대표 사진과 직접 작업 링크를 가진 강조 카드, 다음 4건은 작은 썸네일 목록으로 구분한다. 활성 셀렉·검토 기한이 있는 프로젝트는 대표 카드와 후속 목록 모두 날짜 옆에 공통 `dday()` 계산 결과를 표시한다. 프로젝트 목록과 동일하게 정상 상태는 날짜만, 임박·당일·초과 상태는 `D-N 임박`, `D-day`, `D+N` 강조 텍스트를 함께 보여준다.
- 작업 링크는 `project-next-action.ts`를 프로젝트 목록과 공유한다. 원본 업로드는 upload, 보정·재보정은 assets/retouched로 이동한다. 고객 대기는 프로젝트 상세로 연결한다.
- 최근 프로젝트는 updatedAt 내림차순 최대 3건이며 사진 중심의 ‘최근 변경 프로젝트’로 표시한다. 실제 집계가 없는 재보정 요청 장수는 표시하지 않는다.
- 프로젝트 조회 실패는 오류·재시도 화면으로, 활동 조회 실패는 활동 영역 안의 재시도로 구분한다. 빈 프로젝트 화면도 기존 생성 한도 게이트를 사용한다.
- 대시보드 상단 업무 상황판은 작가 차례 전체와 기한이 지난 고객 차례를 합산한 확인 대상 수를 표시한다. 프로젝트 사용량은 오른쪽 보조 영역의 도넛 차트로 항상 표시하며 기존 quota의 current/max를 사용하고, 관리자 무제한은 프로젝트 목록 건수로 표시한다. 대시보드에서는 전역 사이드바의 중복 사용량을 숨긴다. 상단에 새 프로젝트 버튼을 두고 플로팅 버튼은 표시하지 않는다.
- PC 전용 개선이다. 모바일은 기존 DesktopShell의 프로젝트 목록 리다이렉트를 유지한다. 기존 FocusProjectSection/FocusProjectCard/WorkProjectCard 파일은 남아 있으나 대시보드 페이지에서는 호출하지 않는다.

사진 상세 뷰어는 사진 클릭(모바일 탭)으로 검은 배경의 집중 보기를 전환한다. 집중 보기에서는 헤더·정보 패널·썸네일·이동 버튼을 모두 숨기고 사진만 표시하며, 다시 사진을 누르거나 Escape로 복원한다. 키보드·스와이프 이동은 시각적 버튼 없이 유지한다. 일반 상세 보기의 좌우 버튼은 사진 옆 여백이 충분하면 여백 중앙에, 부족할 때만 사진 위에 배치한다.

원본 비교가 가능한 단일 보정본 보기에서는 사진을 누르고 유지하면 원본을 표시하고, 놓으면 보정본으로 복귀한다. 고객 보정 상세·사진 집중 보기와 작가 원본/보정본 뷰어는 공통 `useHoldPreview`를 사용하며 기본 지연 `DEFAULT_DELAY_MS=300`, 이동 취소 기준 `DEFAULT_MOVE_TOLERANCE_PX=10`을 적용한다. 포인터 캡처와 pointer/touch 종료·창 이탈 복귀도 이 훅에서 함께 처리해 화면별 해제 동작이 갈리지 않는다. 원본은 디코딩 완료 후 별도 레이어로 표시하며, 모바일의 기존 확대 컴포넌트를 교체하지 않는다. 드래그·다중 터치·화면 이탈 시 비교를 취소하고, 길게 누른 제스처는 단일 탭이나 사진 이동으로 처리하지 않는다. 원본 비교를 끝낸 뒤에도 사진만 크게 보는 집중 상태를 유지한다. 일반 상세에서는 PC·모바일 모두 이전/다음 버튼을 표시하고, 집중 보기에서는 버튼을 렌더하지 않는다. 고객·작가 집중 보기 모두 `←`·`→` 사진 이동, `\`을 누르는 동안 원본 보기, `Esc` 일반 상세 복귀를 지원한다. 집중 보기 중에는 아래 상세 화면의 선택·별점·확정·재보정 단축키를 실행하지 않는다. 사진 아래에 사용 안내를 노출하며 PC 단축키 안내는 텍스트 버튼으로 제공한다. 모바일 상단 원본/보정본 버튼은 제거하고 요청·이력의 원본 선택 경로를 유지한다. 헤더·정보 패널·필름스트립·버전 이력의 반복 구분선은 제거하고 다크 배경의 밝기와 여백으로 구분한다.

- 최종 보정본 상세의 수령 모드에서도 하단 `수령 완료` 버튼을 제공한다. 확인 모달에서 전체 보정본 수령을 확인한 뒤 갤러리와 동일한 제출 API로 전체 사진을 approved 처리하며, delivered 응답 시 납품 완료 화면으로 이동한다. 재보정 0회 프로젝트도 상세보기를 유지한다.

- 고객 셀렉 상세뷰어는 PC 필름스트립 옆과 모바일 하단에 선택 수 및 `셀렉 확정하기`를 상시 표시한다. 필요한 장수를 정확히 채웠을 때 활성화하며 기존 확정 확인창과 API를 사용한다. 완료 시 별도 바가 솟아오르지 않는다.

- 유사컷 뱃지는 작가 원본업로드·원본탭·고객 갤러리에서 전체 장수와 펼침 방향으로 통일한다. 펼친 묶음은 중립색으로 표시하고 주황 테두리는 실제 선택에만 사용한다. 펼친 멤버마다 접기 버튼을 제공하며 작가 목록에서도 같은 버튼이 동작한다. 고객은 선택 수를 별도 보조 표시로 제공하고 펼친 동안 선택 변경에 따라 그룹 위치가 이동하지 않는다.
